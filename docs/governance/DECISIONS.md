# FileSetGo Decision Register

This register contains accepted FileSetGo architecture and product decisions. ADR identifiers are unique and must not be reused.

## ADR-001 — Worker-first processing

**Status:** Accepted

Heavy image processing runs in a browser worker. The UI thread may coordinate jobs and render progress, but it must not perform unrestricted decoding, pixel scans, resizing, repeated compression, or full image transforms.

## ADR-002 — Thin Laravel layer

**Status:** Accepted

Laravel owns the product shell, routes, pages, SEO, copy, legal surfaces, and future host policy. It does not own V1 browser-side raster-processing algorithms or introduce premature backend transformation abstractions.

## ADR-003 — Shared `@filesetgo/core` package

**Status:** Accepted

Reusable preflight, safety, worker, processing, validation, and error primitives live in the TypeScript package `@filesetgo/core`. FileSetGo and approved integrations consume the same package.

## ADR-004 — Provisional 15 MB / 24 MP limits

**Status:** Accepted

The initial hard source-file limit is 15 MB and the initial decoded-pixel limit is 24,000,000 pixels. Exactly 6000 × 4000 pixels is accepted. These are provisional engineering defaults pending FSG-006 device benchmarking.

## ADR-005 — HEIC/HEIF input in V1

**Status:** Accepted

HEIC/HEIF is required as a V1 input format. Its implementation must be browser-side, worker-compatible, and lazy-loaded. No specific decoder library is locked until maintenance, security, license, and memory characteristics are evaluated.

## ADR-006 — SVG deferred

**Status:** Accepted

Arbitrary SVG processing is excluded from V1 until a dedicated architecture addresses sanitization, embedded content, external references, fonts, and rasterization behavior.

## ADR-007 — No automatic whitespace trim

**Status:** Accepted

FileSetGo must not automatically remove whitespace or transparent padding as a universal behavior. Trimming is an explicit, previewable operation or preset rule because whitespace can be intentional content.

## ADR-008 — No blind favicon crop

**Status:** Accepted

FileSetGo must not blindly square-crop unsuitable horizontal logos. Guided favicon flows should prefer a square or icon source and provide deterministic suitability guidance.

## ADR-009 — Single active heavy job

**Status:** Accepted

The initial runtime limit is `MAX_ACTIVE_HEAVY_JOBS = 1`. Concurrency may change only after measured device and memory evidence supports a new limit.

## ADR-010 — Zero server ingestion for supported V1 paths

**Status:** Accepted

Supported V1 files are processed entirely on the user's device. Source files, generated outputs, filenames, EXIF metadata, image binaries, and arbitrary image content are not sent to FileSetGo servers or analytics.

## ADR-011 — Keryon package integration

**Status:** Accepted

Keryon consumes `@filesetgo/core` in the browser and uploads only user-approved generated assets to its own storage or CDN. Keryon concepts, authorization, storage, pricing, and cross-promotion remain host responsibilities and do not enter the core package.

## ADR-012 — Canonical `SPRINT_REPORT.md`

**Status:** Accepted

The repository-root `SPRINT_REPORT.md` is the canonical current sprint or checkpoint report. It is overwritten only for a formally governed report; prior versions remain in Git history. Parallel current sprint-report files are not created.

## ADR-013 — Agent-owned routine verification; FSG-006 owns compatibility certification

**Status:** Accepted

Routine sprint verification is the coding agent's responsibility, not the user's. Agents must not ask a human to perform manual QA that the agent can reasonably perform itself — opening DevTools, inspecting network requests, clicking through an engineering proof interface, running browser test cases, verifying image outputs, testing cancellation, or inspecting console errors. Agents instead run the strongest verification available in their environment: unit/integration tests, TypeScript checking, Laravel/PHPUnit tests, production builds, lint/static analysis, and automated browser tooling (Playwright, Claude in Chrome, or equivalent) when usable.

Inability to obtain a manually operated physical browser/device session does not, by itself, block a sprint from closing. Comprehensive real-device and cross-browser compatibility certification (iOS Safari, Android Chrome, Safari desktop, Chrome, Firefox, Edge, memory-pressure and repeated-processing testing) remains assigned to **FSG-006 — Hardening, Mobile QA & Compatibility** and is not a closure requirement for earlier milestones. Earlier milestones should still use browser automation wherever the environment supports it.

## ADR-014 — HEIC/HEIF decoder: `@discourse/heic`

**Status:** Accepted

**Supersedes:** the FSG-001B sprint report's provisional recommendation of `heic-to`. `heic-to` is not technically defective; it was simply not selected. It was never installed in the working tree at any point covered by this decision — its FSG-001B "recommended candidate" status is superseded before any implementation was built against it.

**Chosen decoder:** `@discourse/heic` (npm), pinned at exact version **`1.0.0`** in `packages/core/package.json` (no caret range, to prevent an unreviewed upgrade — `@discourse/heic` has published only this one version, so there is currently nothing to float to, but the declaration is pinned on principle).

**License:** Apache-2.0. No copyleft/LGPL compliance obligations, unlike `heic-to` or `libheif-js`.

**Upstream/provenance:** `@discourse/heic` is Discourse's own npm-scoped publish of the HEIC decoder from `jamsinclair/jSquash` pull request [#101](https://github.com/jamsinclair/jSquash/pull/101) ("HEIC decoder"), opened 2026-03-30 and, as of this decision, still **open and unmerged** upstream (last upstream activity 2026-04-28). Discourse published their fork as `@discourse/heic@1.0.0` on 2026-05-07 — a single release, no patches since. Despite the unmerged upstream status, the package has substantial real-world usage: 33,720 weekly downloads (npm, week of 2026-08-23). Wraps `libheif` + `libde265`, the same codec lineage as `heic-to` and `libheif-js`. Repository: `github.com/discourse/jSquash`. This is a genuine maintenance-continuity risk (single-org fork of an unmerged PR) and is explicitly not dismissed — see Maintenance-Risk Mitigation below.

**Real decode evidence:** the actual installed package was executed directly in Node (via its documented "manual WASM initialization" path — `init(wasmModule)` with a pre-compiled `WebAssembly.Module`, which sidesteps the package's browser/worker environment auto-detection, itself written for classic `importScripts`-style workers rather than the `{ type: 'module' }` worker this project uses):

```
Real synthetic 64×48 HEIC (self-generated, not copyrighted) → SUCCESS
  width=64 height=48 dataLength=12288 (exact 64*48*4 RGBA match), 69ms
Truncated/corrupt HEIC payload (valid header, cut body)      → clean catchable "Decoding error", 1ms
Random garbage bytes                                          → clean catchable "Decoding error", 1ms
Empty buffer                                                   → clean catchable "Decoding error", 0ms
```

No crash, no hang, no uncaught exception in any case — decode failures surface as a plain catchable `Error`.

**Measured bundle/WASM evidence (not speculative):** `codec/dec/heic_dec.wasm` = 959,554 bytes; `codec/dec/heic_dec.js` (Emscripten glue) = 60,964 bytes; total installed package = ~1.0 MB. This must be lazy-loaded so JPEG/PNG/WebP users never pay it — see FSG-001C implementation.

**Output shape:** `decode(buffer: ArrayBuffer): Promise<ImageData>` — a standard, worker-native `ImageData`-shaped result with no DOM dependency, mapping directly onto the existing raster → normalize → resize → canvas → encode → validate pipeline without an intermediate re-encode step.

**Rationale for choosing `@discourse/heic` over `heic-to` in FSG-001C:** `@discourse/heic` was already declared in the workspace (predating this decision), carries a materially more favorable license (Apache-2.0 vs. LGPL-3.0), produced concrete measured bundle-size evidence rather than an estimate, and — critically — was actually executed against real and malformed input with clean, verifiable results. `heic-to` was never executed; only its npm registry metadata was confirmed before its provisional approval was withdrawn. The maintenance/provenance risk of `@discourse/heic` (single-org fork, unmerged upstream PR, one release) is real and is not outweighed by convenience — it is outweighed by the combination of verified technical fit, the license advantage, and the adapter-isolation strategy below, which keeps the specific dependency choice replaceable.

**Maintenance-risk mitigation (binding for FSG-001C implementation):**
1. `@discourse/heic` is accessed only through a narrow FileSetGo-owned adapter (`decodeHeic()`); no other module imports it directly.
2. The adapter is covered by tests exercising success, malformed/truncated/garbage/empty input, decoder-unavailable, and cancellation paths.
3. Test fixtures are self-generated (not third-party photographs) with known pixel dimensions.
4. The package is lazy-loaded — never in the initial application bundle.
5. No undocumented internal API of the package is used; only its public `decode`/`init` exports.
6. If `@discourse/heic` becomes unsuitable later (e.g., the package is abandoned, or the upstream `jSquash` PR merges and supersedes it), replacing it is intended to be a contained change behind the adapter boundary, not a FileSetGo architecture change.

**Governance effect:** `docs/architecture/FORMAT-SUPPORT.md` is updated to reflect `@discourse/heic` as the selected V1 HEIC/HEIF decoder. `ADR-005`'s requirement that "no specific decoder library is locked until maintenance, security, license, and memory characteristics are evaluated" is satisfied by this ADR and the FSG-001C sprint report's dependency audit.

## ADR-015 — FSG-002 target-size engine: bounded search parameters

**Status:** Accepted

FSG-002's directive left several concrete numeric/design choices to implementation judgment ("choose a conservative bound... document the chosen number and rationale"; "define a sensible initial minimum target size... document chosen target validation limits"; "you may choose better names [for unreachable outcomes], but preserve the semantic distinction"). This ADR records those choices as the FileSetGo-specific bounded-search contract, since they materially affect product behavior (how aggressively dimensions shrink, how small a target is honored, how failures are explained) and should not be re-derived or silently changed by a future sprint without a governance update.

**Quality search:** `minQuality = 0.60`, `maxQuality = 0.95` by default (directive-specified). At most **5** encodes per dimension tier. Strategy: try `maxQuality` first (1 probe, exits immediately if it already fits — the best possible outcome); if not, try `minQuality` (2nd probe, exits immediately if even that doesn't fit — no viable quality at this tier); otherwise binary-search the remaining budget between them. This means most real jobs use far fewer than 5 encodes, while 5 remains the hard ceiling.

**Dimension tiers:** each tier scales both dimensions by **0.85** (directive-specified), preserving aspect ratio. **`MAX_DIMENSION_TIERS = 6`** beyond the initial candidate (7 candidates total including tier 0). Rationale: `0.85^6 ≈ 0.377`, so the smallest tier retains ~38% of the original edge length — a 2000px source steps down to ~754px, still a broadly useful web image size. Combined with a **`MIN_DIMENSION_PX = 64`** floor (neither width nor height may drop below this), dimension reduction stops well before an image becomes practically useless, independent of the tier count alone.

**Deterministic maximum encodes per job** (directive §26, with the parameters above): JPEG/WebP HARD = 5; JPEG/WebP FLEXIBLE = 35 (7 tiers × 5 probes); PNG HARD = 1; PNG FLEXIBLE = 7 (1 encode per tier, no quality search).

**Target byte bounds:** `MIN_TARGET_BYTES = 1024` (1 KB) — no real encoded raster image is meaningfully smaller; a smaller request cannot be a genuine target. `MAX_TARGET_BYTES = 15 MB` — exactly the existing FSG-001 source-file safety cap (`DEFAULT_SAFETY_LIMITS.maxInputBytes`); there is no product reason for a target to exceed the largest file the runtime will ever accept as input.

**Structured unreachable outcomes:** two codes are used, not three. `TARGET_UNREACHABLE_HARD_DIMENSIONS` when `dimensionPolicy: 'hard'` and no quality within range meets the target at the one fixed dimension set. `TARGET_UNREACHABLE_MIN_DIMENSIONS` when `dimensionPolicy: 'flexible'` and the full bounded dimension-tier sequence is exhausted (down to the `MIN_DIMENSION_PX` floor or `MAX_DIMENSION_TIERS` limit) without a fitting candidate. A third code, `TARGET_UNREACHABLE_MIN_QUALITY`, is defined in the public contract for API completeness and potential future use, but the current algorithm has no scenario that produces it distinctly from the two above — a smaller dimension tier essentially always makes minQuality's byte size smaller too, so "quality bottomed out" and "ran out of dimension tiers" collapse into the same terminal failure mode in practice. This is a deliberate simplification, not an oversight.

**Governance effect:** these are the authoritative bounds for the target-size engine; changing any of them (e.g., raising `MAX_DIMENSION_TIERS`, lowering `MIN_TARGET_BYTES`) is a product/algorithm change requiring a governing decision, not a routine code change.

None of the above weakens the standing accuracy rule: an agent must never report verification — automated or manual — that did not actually run. This ADR amends the browser/device verification expectations previously stated for FSG-001 in `docs/directives/FSG-001B.md` and `docs/testing/TESTING.md`; it does not restructure the `docs/governance/ROADMAP.md` milestone sequence.

## ADR-016 — FSG-003 public UI: DOM-free orchestration layer, no jsdom

**Status:** Accepted

FSG-003 required both pure UI-logic tests and workflow-orchestration tests (directive §51/§52) without adding a large frontend-test framework (directive §51's own instruction). `jsdom`/`happy-dom` were not already project dependencies, and adding either to unit-test DOM rendering would be a new devDependency requiring separate approval under standing project rules, purely to test code that could instead be structured not to need a DOM at all.

**Decision:** the Quick Fit client (`resources/js/quick-fit/`) is split so that only one module touches `document`:

- `state.ts`, `format-bytes.ts`, `filename.ts`, `errors.ts`, `request-plan.ts`, `summary.ts`, `capabilities.ts`, `validate-form.ts` — pure functions/types, zero DOM and zero `@filesetgo/core` runtime calls beyond type imports. Directly unit-tested (69 tests).
- `workflow.ts` (`QuickFitWorkflow`) — orchestrates file selection, routes a requirement set to `processImage()`/`processImageToTarget()`, tracks the active job, and produces the typed `QuickFitState`. Takes its `@filesetgo/core` bindings (`preflightImage`, `processImage`, `processImageToTarget`, `getRuntimeCapabilities`) as a constructor-injected `QuickFitCoreClient`, mirroring the existing `ImageWorkerFactory` DI pattern in `runtime/worker-client.ts`. Contains no DOM access, so it is directly unit-tested in Node with a fake core client (22 orchestration tests covering routing, cancellation, stale-result prevention, and error/unreachable paths) — no module mocking (`vi.mock`) and no DOM emulation needed.
- `controller.ts` — the only module that queries `document` and binds DOM events to `QuickFitWorkflow`. Not unit-tested; verified via `npm run build` + `npm run typecheck` and, when available, browser automation (ADR-013). This is a deliberately thin layer: it reads form fields, calls `workflow.selectFile()`/`.run()`/`.cancel()`/`.reset()`, and renders `QuickFitState` back into the DOM — it makes no independent decisions `workflow.ts` doesn't already make.

**Governance effect:** future public-UI sprints (FSG-004+) should follow the same shape — DOM-free pure/orchestration modules covered by Vitest, a thin DOM-binding controller left to build/typecheck/browser-automation verification — rather than introducing `jsdom`/Testing-Library/Playwright component testing to unit-test DOM rendering directly. Introducing a DOM-emulation test dependency remains available if a future sprint's UI complexity genuinely outgrows this pattern, but requires the standing dependency-change approval, not a default.

**TypeScript project boundary (final architecture).** Including `resources/js/quick-fit/tests/**` in the root production `tsconfig.json` (its `include: ["resources/js/**/*.ts", ...]` matches everything under `resources/js/`) would pull `vitest`'s own type-declaration graph into the same TypeScript project as production browser code — a real environment mismatch (test-runner/Node-facing types leaking into the project that represents what ships to the browser), not merely a compile inconvenience. An initial attempt to paper over the resulting errors with root-level `"skipLibCheck": true` was rejected: it addressed the symptom (declaration-file errors) without fixing the actual boundary problem, and applied a lib-check exemption globally to the production project rather than scoping it to where it was actually needed.

The corrected, final structure:

- **`tsconfig.json`** (root, production/browser) — unchanged `compilerOptions` (`types: ["vite/client"]`, no `"node"`), plus an explicit `"exclude": ["resources/js/quick-fit/tests/**"]`. This project represents shipped browser code only; it never sees Node globals or Vitest's types, and no `skipLibCheck` was added to it.
- **`tsconfig.ui-tests.json`** (new, root) — a dedicated project for the Quick Fit test environment: `include: ["resources/js/quick-fit/**/*.ts"]` (both the pure/orchestration source modules and their `tests/*.test.ts` files, so the project is self-contained and typechecks cleanly on its own), `types: ["node"]` (this project legitimately needs Node ambient types, since `vitest`'s own public type surface references them). No `skipLibCheck` here either.
- **`@types/node`** — added as a **devDependency**, used only by `tsconfig.ui-tests.json`'s `types` array. Never reaches the production root project. Not a runtime Node dependency; FileSetGo's shipped browser code does not use Node APIs.
- `npm run typecheck` now runs all four TypeScript projects in sequence (root, `packages/core/tsconfig.json`, `packages/core/tsconfig.worker.json`, `tsconfig.ui-tests.json`); `npm run typecheck:ui` runs just the UI-test project directly.

**A second, independent problem this then exposed (not caused by the above):** with `skipLibCheck` genuinely gone from the root project and `@types/node` correctly supplying Node types, full declaration checking of `tsconfig.ui-tests.json` still failed with `TS2300: Duplicate identifier 'containSubset'`. This is a real upstream defect, unrelated to FileSetGo's own configuration: **Vitest 3.2.7** (the version this project has installed; confirmed to be the latest published 3.x patch — only 4.x/5.x major versions are newer) bundles its own `dist/chunks/global.d.ts`, which declares `Chai.Assert.containSubset` as a property-typed field. Vitest's own `package.json` simultaneously requires `"@types/chai": "^5.2.2"`, and `@types/chai` 5.2.x independently declares that same member as a method. The two declaration styles are not mergeable, so TypeScript reports a duplicate identifier whenever *any* project imports from `vitest` 3.2.7 under full (non-`skipLibCheck`) checking — this is very likely why `packages/core/tsconfig.json`'s pre-existing `skipLibCheck: true` (predating FSG-003, left untouched by this sprint) has been silently absorbing this exact conflict since FSG-001, not only the `node:` built-in imports it was originally documented for.

**Resolution:** a root `package.json` `"overrides"` entry pins the transitive `@types/chai` to `5.0.1` — the last version published before it gained `containSubset` typings at all, which removes the conflicting declaration rather than reconciling it:

```json
"overrides": {
  "@types/chai": "5.0.1"
}
```

This is **types-only** and resolves to a nested `vitest/node_modules/@types/chai` — it does not affect the real `chai`/`vitest` packages used at runtime, and FileSetGo code (production or test) does not import `chai` directly or use `containSubset` anywhere (confirmed by repository-wide search), so there is no behavioral surface. With it in place, `npm run typecheck` passes with **zero errors and zero `skipLibCheck` anywhere** in the four-project chain; `npm ci` followed by the same command reproduces this cleanly from the lockfile.

**This override is accepted as a temporary, governed toolchain-compatibility pin, not a permanent dependency-architecture decision.** It sits outside Vitest's own declared `@types/chai` semver range (`^5.2.2`), which is inherently a form of risk (a future transitive change could re-surface friction differently), even though the empirical evidence above shows no current fallout. **Removal trigger:** the next time FileSetGo upgrades Vitest to a new major version, first try removing this override; if the newer Vitest's bundled declarations no longer conflict with a current `@types/chai`, remove it. This does not need its own dedicated sprint unless removal turns out to be non-trivial.

## ADR-017 — FSG-005A multi-output packaging foundation

**Status:** Accepted

FSG-005A required a genuine architectural addition — not just new data or UI, but a new heavy-job kind (`processImageSet()`) sharing the existing worker/runtime infrastructure, a new dependency (`fflate`) for ZIP archive creation, and new safety limits. This ADR records the resulting architecture as the authoritative reference for FSG-005B and later packaging work.

**One decode, many outputs.** `processImageSetInWorker()` (`packages/core/src/workers/process-image-set.ts`) preflights and decodes the source exactly once, then reuses the shared FSG-001 primitives (`decodeSourceToBitmap`, `createRenderCanvas`, `drawBitmapToCanvas`, `validateOutput`) to produce each requested output sequentially — never in parallel, and never via repeated `processImage()` calls. Each output's canvas is released before the next is created, so peak memory stays bounded by one canvas at a time regardless of how many outputs are requested, exactly like the FSG-002 target-size engine's own dimension-tier loop.

**A third job kind, one shared slot.** `ImageProcessingRuntime` (`runtime/worker-client.ts`) gained a `'set'` `JobVariant` alongside the existing `'standard'` and `'target'` kinds. `MAX_ACTIVE_HEAVY_JOBS = 1` now holds across all three — starting any job kind cancels whichever job (of any kind) is currently active. This required extending, not duplicating, the existing single-job-slot state machine (`beginJob`/`start`/`handleWorkerEvent`/`finish`).

**Package safety bounds** (`processing/image-set-limits.ts`): `MAX_PACKAGE_ASSETS = 16` and `MAX_PACKAGE_TOTAL_OUTPUT_BYTES = 50 * 1024 * 1024` (50 MiB). The asset-count limit is enforced before any processing begins (`validate-image-set-request.ts`); the byte limit is enforced progressively as each output is produced (`process-image-set.ts`), since only the encoder — not the request — knows a given output's final size. Both are initial engineering limits, not marketing promises, matching the framing already established for FSG-001's 15 MB/24 MP limits (ADR-004).

**ZIP library: `fflate@0.8.3`, exact-pinned, MIT licensed.** Approved by the project owner for this sprint specifically (directive §20); verified before installation (name `fflate`, version `0.8.3`, license **MIT**, zero runtime dependencies) and again after (`npm ls fflate` resolves exactly `fflate@0.8.3`). Hidden entirely behind `packages/core/src/archive/zip-adapter.ts` — the only module in FileSetGo that imports `fflate` directly. No `fflate` type, option, or callback appears in any public `@filesetgo/core` export; `createZipArchive()` is not exported from `index.ts` at all (it is a worker-internal implementation detail, used only by `process-image-set.ts` via a lazy dynamic `import()`).

**ZIP strategy:** flat archives only (no directory trees) — enforced by `archive/filename-safety.ts`'s `isSafeArchiveEntryName()`, which rejects any `/`, `\`, or `:` character outright (covering traversal, absolute paths, and drive-letter paths in one check) alongside empty names, `.`, `..`, and null bytes. Every entry uses ZIP STORE (`level: 0`) rather than DEFLATE, since package contents are already-compressed JPEG/PNG/WebP bytes — spending CPU re-compressing them would be wasted work. Every entry (and the archive's own internal timestamp field) uses a fixed deterministic `mtime` (1980-01-01, the ZIP format's own epoch) rather than `fflate`'s current-time default, so identical entries/order reliably produce identical archive bytes (verified directly in `zip-adapter.test.ts`).

**Lazy-loaded, verified by build inspection.** `zip-adapter.ts` (and therefore `fflate`) is only reached through `process-image-set.ts`'s dynamic `import('../archive/zip-adapter')`, itself only invoked when an image-set job actually requests an archive. The production build confirms this: `fflate`'s minified DEFLATE table-building code appears only in its own `zip-adapter-*.js` chunk (9.12 kB), with zero occurrences in `app-*.js` or `image.worker-*.js`. Quick Fit and Guided Fit do not call `processImageSet()` in this sprint (no public UI exists yet — directive §29), so ordinary visitors never load any of this code.

**Governance effect:** FSG-005B must reuse `processImageSet()`/`compilePreset`-style compilation into `ImageSetOutputSpec[]` for the Website Logo Pack rather than introducing a second processing or packaging architecture. Product-specific concepts (favicon, Apple touch icon, Logo Pack naming) belong entirely in a future `resources/js/logo-pack/`-style product layer, exactly as FSG-004's preset knowledge lives in `resources/js/presets/` rather than `@filesetgo/core`.

## ADR-018 — FSG-005B Website Logo Pack: exact composition, fixed-canvas contain, ICO architecture, controlled upscaling

**Status:** Accepted

FSG-005B introduced several concrete numeric/architectural choices the directive left to implementation judgment. This ADR records them as the authoritative Logo Pack contract.

**Exact package composition** (directive §13, `resources/js/logo-pack/spec.ts`): exactly seven public assets, in this order — `logo-header.png`, `logo-header@2x.png`, `favicon.ico`, `favicon-32x32.png`, `apple-touch-icon.png`, `icon-192x192.png`, `icon-512x512.png`. No README, no manifest, no HTML snippet ships in this milestone (directive §44/§45) — a web manifest specifically requires site/application metadata FileSetGo doesn't have yet; this is deferred, not forgotten.

**Header bounds:** standard header bounding box 400×120px, high-density header bounding box 800×240px (directive §15/§16). Both use the existing FSG-001 resize-fit behavior (`RasterImageSetOutputSpec` with `resize`) — preserve aspect ratio, no crop, no stretch, no upscale beyond source resolution.

**Fixed-canvas CONTAIN primitive** (`packages/core/src/transforms/contain.ts`, directive §17): a new, genuinely generic core primitive — `calculateContainPlan(sourceWidth, sourceHeight, canvasWidth, canvasHeight, contentScale, allowUpscale)` returns a deterministic draw plan (size + centering offset + applied scale). It has no concept of icons or Logo Pack; it is reusable by any future workflow needing "source → contain → fixed canvas." Rendering reuses the existing `scaledTransform()` helper from FSG-001 unchanged (`workers/process-image-set.ts`'s `drawBitmapContained()`), only adding a translation offset to center the content — no new transform math was needed.

**Content box is deterministically floor-rounded, corrected post-implementation:** the content box a source may occupy is `Math.floor(canvasWidth * contentScale)` × `Math.floor(canvasHeight * contentScale)` — an integer pixel box computed *before* it drives the scale calculation, not the fractional `canvasWidth * contentScale` value used directly. The original FSG-005B implementation used the fractional value directly (e.g. `512 * 0.9 = 460.8` fed straight into the scale division); this was corrected in a subsequent completion-audit pass because a fractional content box is not equivalent to a floored one and is not reproducible in whole pixels. Required evidence (a square source matching a square canvas, `allowUpscale: true`, so `drawWidth`/`drawHeight` equal the content box exactly): 32px canvas → 28px box, 180px → 162px, 192px → 172px, 512px → 460px — all asserted directly in `contain.test.ts`. This is the authoritative formula going forward for every Logo Pack icon canvas.

**`ICON_CONTENT_SCALE = 0.90`** (directive §18): every square icon asset's artwork may occupy at most 90% of its canvas on the constraining axis (floor-rounded per above), centered, transparent background, never cropped/stretched/auto-trimmed.

**Controlled icon upscaling, `MAX_ICON_UPSCALE_FACTOR = 4`** (directive §23): icon/favicon `ImageSetOutputSpec`s are compiled with `allowUpscale: true` — an explicit, narrow exception to FileSetGo's general no-upscale convention, safe only because the product layer's suitability evaluator (`resources/js/logo-pack/suitability.ts`) computes the exact required scale factor against the 512px icon canvas *before* any processing begins (reusing `calculateContainPlan(..., allowUpscale: true).scale` purely as a scale calculator, not a render call) and refuses to start generation (`SOURCE_TOO_SMALL_FOR_LOGO_PACK`-equivalent blocking issue) when that factor exceeds 4×. `factor <= 1` → good; `1 < factor <= 4` → warning, generation proceeds; `factor > 4` → blocking.

**Geometry warning threshold `2.5`** (directive §25): `aspectRatio = longerEdge / shorterEdge`; a warning (never a block, never an automatic crop) appears above 2.5, exactly at 2.5 is not warned.

**ICO architecture** (`packages/core/src/icons/ico.ts`, directive §28–§31): a small, dependency-free, FileSetGo-owned ICO container reader/writer — `createIco()`/`validateIcoContainer()` — entirely generic (no "favicon" concept). Every entry is PNG-compressed (never legacy BMP/DIB). `favicon.ico` is compiled as one `IcoImageSetOutputSpec` with three independently CONTAIN-rendered entries (16/32/48px, `ICON_CONTENT_SCALE`, controlled upscale) — the governed 16/32/48 requirement is a Logo Pack *product* decision (`spec.ts`'s `ICO_ENTRY_SIZES`), not something the generic core validator enforces; `validateIcoContainer()` independently re-parses raw bytes from scratch (never trusts `createIco()`'s own internal state) and accepts any valid entry set. `process-image-set.ts` additionally checks the produced ICO's actual entries match what was *requested* before accepting the asset, and fails the whole image-set job if either check fails (`ICO_VALIDATION_FAILED`).

**`ImageSetOutputSpec`/`ImageSetAssetResult` became discriminated unions** (`'raster' | 'contain' | 'ico'` / `RasterAssetResult | IcoAssetResult`) to accommodate ICO's fundamentally different shape (a size *set*, not a single width/height) — a genuine, intentional breaking change to FSG-005A's contract, safe because FSG-005A shipped with zero UI consumers of `processImageSet()`. `processImage()`/`processImageToTarget()` were not touched.

**Product/core boundary held:** `@filesetgo/core` gained only generic capabilities (contain, ICO container format) with zero knowledge of "logo," "favicon," "header," or "Logo Pack." All of that lives in `resources/js/logo-pack/` (`spec.ts` for the composition catalog, `suitability.ts` for geometry/resolution/transparency assessment, `compiler.ts` for translating the catalog into a `ProcessImageSetOptions`, `logo-pack-controller.ts` for orchestration) — mirroring the exact `resources/js/presets/` pattern FSG-004 established.

**Shared workspace-mode ownership extended, not duplicated:** `GuidedFitController` (FSG-004) already owned Quick-Fit/Guided-Fit mode-tab state; rather than introduce a second, competing mode-state owner for Logo Pack, its `QuickFitMode` type gained a third `'logo-pack'` value and its constructor gained an optional `isExternallyBlocked` callback (used to also block mode-switching while a Logo Pack job is active) — `GuidedFitController` still doesn't import `LogoPackController` directly; `controller.ts` wires the callback.

**Governance effect:** any future asset-generation workflow needing a fixed-canvas render should use `calculateContainPlan()`/`ContainImageSetOutputSpec` rather than inventing a parallel primitive. Any future icon-container work should use `packages/core/src/icons/ico.ts` rather than a new dependency. Changing any of the governed numeric values above (content scale, upscale factor, geometry threshold, header/icon bounds, the seven-asset composition) is a product decision requiring a governance update, not a routine code change.

## ADR-019 — FSG-006 browser compatibility infrastructure and a real Logo Pack defect found by it

**Status:** Accepted

FSG-006 introduced real, permanent browser-test infrastructure and, in the process of using it, found and fixed a genuine defect that 307 passing Vitest unit tests had never exercised. Both are material, long-lived decisions recorded here.

**Playwright is the permanent browser-test framework** (`@playwright/test`, dev-only dependency; directive §8/§67). `tests/browser/` is a dedicated boundary, separate from `packages/core/tests`/`resources/js/**/tests` — it runs the real, built, locally served application (`php artisan serve` over the production Vite build) end-to-end, never a synthetic reimplementation of controller logic. `playwright.config.ts` defines `chromium`/`firefox` projects for full functional certification plus four Chromium-based mobile-viewport projects (`mobile-narrow-320`, `mobile-iphone-class`, `mobile-android-class`, `mobile-tablet-class`) for the dedicated responsive-layout suite (directive §11–§14).

Corrected: `package.json` now declares `"1.55.1"` exactly, `package-lock.json` was regenerated to match through the normal governed `npm install` workflow (not the CI-only lockfile-dropping path), and `npm ci` + `npm ls @playwright/test` were verified to resolve exactly `@playwright/test@1.55.1` locally. What is real and unavoidable is a narrower, purely environmental fact: this coding agent's local macOS 12 (Monterey) host cannot run a current, non-CVE-affected Playwright WebKit build at all. Investigated in detail:

Per directive §11, exact device branding matters less than the product behaviors being verified (no horizontal overflow, reachable controls, tap targets, stacking). **This mobile-viewport emulation is not, and does not claim to be, physical-device certification** — it proves CSS/layout/touch-target behavior at real device dimensions, not real-device hardware, GPU, memory, or OS-integration behavior.

The governed engine targets for FSG-006 are **Chromium, Firefox, and WebKit** — all three, per the paragraph above.

It applies only to this one dedicated tsconfig; the main `tsconfig.json`, `tsconfig.ui-tests.json`, and `tsconfig.worker.json` are untouched and still have no such exception. **Removal trigger:** when Playwright and/or the project's TypeScript version is next upgraded, first test removing this exception. **A real, confirmed production defect was found and fixed:** `packages/core/src/runtime/protocol.ts`'s `isImageSetAssetResult()` validated every `ImageSetAssetResult` against the raster-only shape (`isProcessedImageResult()`, requiring `width`/`height`/`format`) unconditionally. `IcoAssetResult` (`kind: 'ico'`, favicon.ico) has none of those fields — it carries `sizes: number[]` instead. Fixed by making `isImageSetAssetResult()` branch on `kind` (`'ico'` → validate the actual `IcoAssetResult` shape; otherwise → the existing raster check), with new regression coverage in both `protocol.test.ts` (positive: raster+ICO mix accepted; negative: malformed ICO still rejected) and `worker-client.test.ts` (a full runtime round-trip resolving a mixed-asset result). This is exactly the class of defect FSG-006 exists to catch: a real cross-realm structured-clone/validation boundary that mocked unit tests never crossed.

**A real responsive defect was found and fixed:** the mode tabs (`#mode-tab-quick-fit`/`-guided-fit`/`-logo-pack`) used `min-h-9` (36px), short of the ~44px touch-target guideline directive §13 names them under explicitly — measured at ~40px effective height at a 320px viewport. Changed to `min-h-11` (44px), matching every other primary control in the app. Separately, the Logo Pack asset list's per-row download button rendered its full `Download {filename}` label with `whitespace-nowrap`, forcing that button (and the page) wider than a 320px viewport once a real filename was present. Fixed by shortening the *visible* label to "Download" (the filename is already shown above it in the row) while keeping the full, distinct `Download {filename}` as the `aria-label` — this also removed redundant on-screen text, not just the overflow.

**Governance effect:** any future `ImageSetAssetResult`-shaped discriminated union added to the worker protocol must have its own branch in `isImageSetAssetResult()`, not fall through to the raster check. Any future protocol-envelope test fixture representing a real product result must use the *actual* shape a real workflow produces (all its asset kinds), not a simplified stand-in — a simplified fixture is exactly what let this defect ship past 304 passing tests. `tests/browser/` is now a required, permanent part of the verification surface for any change touching the worker protocol, the Logo Pack UI, or responsive layout, not a one-off FSG-006 artifact.

**CI is verification infrastructure, not a deployment pipeline.** `.github/workflows/fsg-006-browser-certification.yml` exists to obtain a real WebKit (and cross-validated Chromium/Firefox) result on a supported runner; it builds and serves the application only to run the same Playwright suite against it, publishes nothing, and does not touch any production or staging environment. No second browser-test framework was introduced to solve the WebKit gap. **Its dependency install is not currently lockfile-reproducible** (it drops `package-lock.json` to work around the `npm/cli#4828` rolldown optional-dependency bug — see the correction above) — an open FSG-006 infrastructure limitation, to be resolved with a real cross-platform fix (not a hard-coded native-binding package guess) before FSG-006's final certification, recorded honestly rather than solved by accident.

## ADR-020 — FSG-005C Logo Transparency Preparation & Verification

**Status:** Accepted

**Supersedes, narrowly:** the "no background removal" element of FSG-005B's contract — `docs/directives/FSG-005B.md` §109 ("automatic background removal" listed as explicitly out of scope) and §1673 ("No background removal exists") — as governed by ADR-018. **ADR-018 itself is not rewritten, edited, or deleted**; it remains the accurate historical record of what FSG-005B actually shipped and why (fixed-canvas CONTAIN, ICO architecture, controlled upscaling — none of that is touched or superseded). Only the single behavioral claim "FileSetGo does not perform background removal" is superseded, by this ADR, for Logo Pack's Transparent mode only.

**Why:** a real user tested Website Logo Pack expecting a transparent logo and did not get one. FSG-005B's contract — preserve an uploaded background, only preserve transparency that already existed — was accurate to what was built and directed at the time, but is a real product defect against what users actually need from a "transparent logo" feature. See `docs/directives/FSG-005C.md` §1/§2.

**Explicit background choice, never inferred (directive §5):** Logo Pack now asks the user directly — *Transparent background* or *Keep existing background* — before generating anything. `LogoBackgroundMode = 'transparent' | 'original'` (`resources/js/logo-pack/spec.ts`) is never derived from source format, PNG/JPEG-ness, or decoded alpha capability, and no mode is preselected. Replacing the source invalidates the choice entirely (`LogoPackController.clearOwnState()`) — File A's mode can never authorize File B's packaging.

**Original mode preserves the uploaded background exactly** (directive §7) — it does not force opacity. An already-transparent PNG selected under Original mode stays transparent; FileSetGo is preserving supplied artwork, not manufacturing an opaque result. The existing FSG-005A/FSG-005B packaging pipeline runs unchanged, sourced from the original file.

**Transparent mode is a two-stage pipeline** (directive §8/§31): *prepare-and-verify a transparent master* (PNG, always) → *preview* (the same Blob, three backgrounds) → user proceeds → *package* (the verified master, decoded once, feeds the existing multi-output pipeline exactly as FSG-005A/FSG-005B already do for any other source). The master is never regenerated during packaging — packaging decodes it once, per the pre-existing "one source → one decode → multiple outputs" invariant.

**Actual pixel alpha inspection, never inferred (directive §9):** `packages/core/src/transforms/alpha-inspection.ts` exports a generic `inspectAlpha(raster)` — a full-scan (not sampled) pixel-alpha classifier (`'opaque' | 'transparency-present'`, plus sampled/fully-transparent/semi-transparent pixel counts and min/max alpha). It has zero "logo"/"background"/"transparent" terminology — it answers only "does this decoded raster actually contain alpha transparency," the same question for any future FileSetGo feature that might need it. Format/extension/MIME/encoder capability are never treated as evidence.

**Correction: alpha presence is not background-transparency readiness (Product Office review, post-implementation).** The first FSG-005C implementation bypassed background removal whenever `inspectAlpha()` reported `'transparency-present'` anywhere in the source. Product Office identified that this could recreate the milestone's own motivating defect under a different technical condition: a PNG with a thin transparent margin around an otherwise-opaque, un-removed rectangular background genuinely contains alpha, but its actual background was never removed — bypassing on alpha presence alone would report "Transparent background verified" for a background that is still there. `packages/core/src/transforms/background-transparency.ts` adds a second, still generic, connectivity-based assessment — `assessBackgroundTransparency(raster)` — that `inspectAlpha()` itself is deliberately *not* modified to perform (directive §2: keep the narrow primitive narrow). It answers a different question: "does the existing alpha already represent a sufficiently meaningful, prepared transparent background to safely skip removal?", via `ExistingTransparencyStatus = 'opaque' | 'alpha-present-background-not-confirmed' | 'background-transparency-confirmed'`. The algorithm: (1) flood-fill from the image border through non-opaque pixels only (alpha-based connectivity, no colour check) to get `boundaryConnectedTransparentRatio` — below `MIN_BOUNDARY_TRANSPARENT_RATIO = 0.03`, any alpha present is incidental (a stray pixel or tiny corner), never confirmed; (2) of the pixels NOT covered by that flood, estimate the colour of the "shoreline" (opaque pixels immediately adjacent to the transparent region) and flood-fill outward from it by colour similarity, confined to that remaining domain — the fraction it does *not* reach (`residualForegroundRatio`) is a distinctly-coloured region trapped behind the already-transparent margin; above `MAX_RESIDUAL_FOREGROUND_RATIO_FOR_CONFIRMATION = 0.03`, that is real evidence of an unremoved background wrapping further artwork, never confirmed. Both thresholds were derived from constructed fixture evidence (`background-transparency.test.ts`), not chosen arbitrarily: a single transparent pixel or a 3×3 transparent corner produced a boundary ratio of 0 and ~0.006 respectively; every genuine transparent-foreground fixture tested produced a residual of exactly 0; the transparent-padding-around-an-opaque-background regression fixture produced residual ratios from ~0.08 to ~0.69 across several rectangle/artwork proportions tested. `removeConnectedBackground()` itself was made existing-alpha-aware to correctly handle the "not confirmed" case (a source that already carries some real transparency but needs further preparation): a pixel already non-opaque is automatically treated as background-like for seeding/flood purposes (no colour check needed — it is already transparent), and the background-colour estimate falls back to the "shoreline" when the literal border carries no opaque pixels to sample from. For the overwhelmingly common fully-opaque source, both of these are no-ops — verified directly: all 14 pre-existing `background-removal.test.ts` cases continued to pass unmodified after this change. Post-encode verification additionally re-runs the lighter boundary-connectivity check (not the full residual assessment, which would misclassify a successfully-processed multi-coloured logo) against the actual encoded output, downgrading a `verified` result to `needs-review` if the final file's connected transparent margin is not real evidence of a background, not merely one surviving pixel (directive §9). See `SPRINT_REPORT.md`'s "Transparency-Readiness Correction" section for the full worked evidence, including why a purely geometric/colour-based signal cannot perfectly distinguish a wrapped-background case from a legitimately multi-coloured logo with an interior design detail (an intrinsic ambiguity, resolved by erring toward re-running preparation rather than risking a false bypass).

**Deterministic, connectivity-aware background removal — not a global colour threshold (directive §12/§13):** `packages/core/src/transforms/background-removal.ts`'s `removeConnectedBackground(raster, strength)` is a real, bounded algorithm: (1) estimate the background colour from the median of the image's own border-ring pixels; (2) an iterative (non-recursive, bounded-stack) BFS flood-fill seeded only from border pixels within a strength-dependent colour-distance threshold, propagating only through 4-connected neighbours also within that distance; (3) every flood-reached pixel becomes fully transparent; (4) pixels within a small radius of the flood region get a *soft*, non-binary alpha ramp plus RGB decontamination (the standard "unblend from a known background" formula), rather than a hard 0/255 cliff. Because the flood only ever propagates from a path of background-like pixels connected to the border, a disconnected foreground region survives even when its colour closely matches the background — this is the specific property that rules out "delete every white/black/near-background pixel" as an implementation, which the directive explicitly forbids (§12).

**Removal strength is a non-expert, three-value control (directive §15):** Gentle/Balanced/Strong map to `BACKGROUND_REMOVAL_THRESHOLDS = { gentle: 18, balanced: 34, strong: 55 }` (Euclidean RGB colour-distance, out of a maximum possible ~441). No numeric threshold, tolerance, or algorithm name is ever exposed to the user. Balanced is the governed default the moment the user chooses Transparent; changing strength regenerates the master and preview. The selector is hidden entirely when the source already has real transparency (`removalApplied === false`), where it would be meaningless.

**Edge decontamination prevents colour-fringed halos (directive §14):** an anti-aliased edge already blended against the old background before this pipeline ever runs would otherwise leave a visible white/black/coloured fringe if only its alpha were reduced. Pixels within the soft-edge radius are decontaminated using `observed = alpha·fg + (1-alpha)·bg ⇒ fg = (observed - (1-alpha)·bg) / alpha`, recovering an estimate of the true foreground colour rather than leaving the background bleeding through.

**Tri-state confidence, never a false "clean success" (directive §16):** `TransparentMasterStatus = 'verified' | 'needs-review' | 'failed'`. `verified` means genuine mechanical alpha verification passed and no known strong ambiguity signal was found — never a visual-quality guarantee. `needs-review` means a real transparent result exists but should be inspected (non-flat background, ambiguous border, marginal removal). `failed` means no technically acceptable transparent master could be produced at all, and blocks packaging outright. Thresholds (`packages/core/src/workers/process-transparent-master.ts`): remaining-opaque ratio < 2% → `failed` (`insufficient-remaining-foreground`); removed ratio < 1% when removal was attempted → `needs-review` (`no-meaningful-background-change`); border colour-variance > 40 → `needs-review` (`non-flat-background`); border-seed rejection ratio > 25% → `needs-review` (`ambiguous-border`). These are derived from the fixture matrix in `SPRINT_REPORT.md`, not invented to pass tests (directive §26).

**Common cases are held to a real quality bar, difficult cases may legitimately not be (directive §17/§18):** flat white/black/coloured backgrounds, anti-aliased marks, thin typography, and normal curved icon edges are required to reach `verified` — the fixture matrix in `SPRINT_REPORT.md` proves this, not merely a status check. Gradients, drop shadows, semi-transparent elements, and near-background-coloured foreground are acknowledged difficult cases that may legitimately land on `needs-review`/`failed`; what is never acceptable is a destructive removal masquerading as a clean `verified` result.

**Post-encode verification is mandatory, never trusting only the pre-encode canvas (directive §24):** after encoding the transparent master PNG, the worker re-decodes the actual encoded `Blob` (`createImageBitmap` → fresh canvas → `getImageData`) and re-runs `inspectAlpha()` on that real output. If the encoded file does not actually contain transparency, the result is `failed` (`encoded-output-opaque`) regardless of what the pre-encode canvas looked like — this catches an encoder silently flattening alpha, the wrong Blob being passed, or any other output/state mismatch, mirroring exactly the class of defect ADR-019 found in the worker protocol layer.

**Transparency-aware preview, one Blob, three contexts (directive §27):** the product layer renders the same generated transparent-master `Blob` against a real CSS checkerboard (`.fsg-checkerboard` in `resources/css/app.css`, a `conic-gradient`, never a baked-in checkerboard image), a light background, and a dark background — toggled by CSS class changes on the preview frame, never three different generated images.

**Bounded working raster, not the 24 MP safety ceiling (directive §19):** `TRANSPARENT_MASTER_MAX_DIMENSION = 1024` (`packages/core/src/workers/process-transparent-master.ts`) — Logo Pack's largest real outputs are the 800px high-density header and the 512px largest icon, so 1024px gives comfortable headroom while keeping worst-case memory small (a 1024×1024 RGBA buffer is 4 MiB; the pipeline holds only a small, bounded number of such buffers — the working canvas's `ImageData`, the background-removal output buffer, and, transiently, the small encoded PNG's post-encode re-decode). This is a separate, much smaller bound than ADR-004's global 24 MP decoded-pixel safety ceiling, specific to this stage's actual output requirements — it does not change ADR-004.

**Shares the single active-heavy-job runtime slot (directive §20/§21):** a fourth job kind, `'transparent-master'`, was added to `ImageProcessingRuntime`'s existing discriminated `JobVariant` union (`packages/core/src/runtime/worker-client.ts`) alongside `'standard'`/`'target'`/`'set'` (ADR-009's single-active-heavy-job invariant). Starting a transparent-master preparation job cancels whatever job — of any kind, from Quick Fit, Guided Fit, Logo Pack packaging, or a previous transparent-master preparation — is currently active, and vice versa. No new runtime, no parallel job queue.

**A new protocol event got its own dedicated validator, reapplying ADR-019's lesson directly:** `TransparentMasterResult` is not a `ProcessedImageResult`/`ImageSetAssetResult` shape (no `sourceDimensions`/`normalizedDimensions`/`resized`). `isTransparentMasterResult()` (`packages/core/src/runtime/protocol.ts`) is a new, dedicated shape validator for `JOB_COMPLETE_TRANSPARENT_MASTER` — deliberately never routed through `isProcessedImageResult()` — precisely to avoid repeating the exact defect class ADR-019 documents (a validator silently rejecting a real result shape it was never updated to recognize).

**Exact new file-naming contracts, both modes still exactly seven assets (directive §32/§33):** given a safe source basename (path separators/null bytes stripped, traversal-only names and empty names fall back to `"logo"` — `extractSafeBasename()` in `spec.ts`), Transparent mode produces `{basename}-transparent.png`, `{basename}-transparent@2x.png`, `favicon.ico`, `favicon-32x32.png`, `apple-touch-icon.png`, `icon-192x192.png`, `icon-512x512.png`, archived as `{basename}-filesetgo-transparent-logo-pack.zip`; Original mode produces the same seven-asset shape with `-original`/`-original@2x` primary filenames and a `{basename}-filesetgo-original-logo-pack.zip` archive. `favicon.ico` and the fixed icon filenames are unchanged and mode-independent, per directive §34. This intentionally changes FSG-005B's fixed `logo-header.png`/`logo-header@2x.png` naming — a deliberate, directive-mandated contract change, not a regression.

**No server involvement, no new dependency (directive §11/§39):** all inspection, removal, encoding, and verification happen inside the existing browser worker architecture — no network request, no server-side processing, for either mode. No ML/segmentation/matting model or WASM/native dependency was added or evaluated as necessary; the boundary-informed connected-removal algorithm is standard-library TypeScript/Canvas only, consistent with FSG-005C directive §39's dependency-approval boundary (STOP and report to Product Office before installing anything, if ever needed).

**Product/core boundary held (directive §38):** `inspectAlpha()`/`removeConnectedBackground()`/`processTransparentMasterInWorker()` carry zero "Logo Pack"/"logo"/"header"/"favicon" terminology — they are as generic as `calculateContainPlan()`/the ICO container format were for FSG-005B (ADR-018). All Logo Pack–specific naming, mode state, and UI orchestration live in `resources/js/logo-pack/` and `resources/js/quick-fit/controller.ts`, mirroring the existing pattern.

**Governance effect:** any future feature needing "does this raster have real transparency" should use `inspectAlpha()` rather than inferring from format. Any future feature needing "does this raster's existing transparency already represent a prepared background" should use `assessBackgroundTransparency()` rather than trusting `inspectAlpha()`'s classification alone — the two answer genuinely different questions, and conflating them is exactly the defect class this ADR's correction fixes. Any future feature needing deterministic, connectivity-aware foreground/background separation should extend `removeConnectedBackground()`'s approach rather than inventing a global-threshold shortcut — ADR-018's ICO/CONTAIN precedent and this ADR both establish that Logo Pack-adjacent generic primitives belong in `@filesetgo/core`, not the product layer. Any future worker-protocol result shape must get its own dedicated validator per ADR-019's lesson, now reapplied twice. Changing the removal thresholds, the bounded working dimension, the background-transparency-assessment thresholds, or the tri-state confidence rules is a product decision requiring a governance update, not a routine code change.

## ADR-021 — FSG-006 delta recertification: CI dependency-install reproducibility fixed at the lockfile, not by hard-coding a native package

**Status:** Accepted

**The problem, traced rather than guessed (directive §10):** `.github/workflows/fsg-006-browser-certification.yml`'s Node-dependency-install step previously deleted `package-lock.json` and ran a fresh `npm install` on the CI runner, working around an install failure but making the CI run's actual dependency graph unprovable — exactly the reproducibility gap ADR-019 recorded as an open FSG-006 limitation. The install failure itself was investigated directly: `vite@8.2.2` (this project's installed `^8.0.0`) depends directly on `rolldown@1.2.7`, which declares all 15 of its platform-native binding packages (`@rolldown/binding-{platform}-{arch}[-{libc}]`) as `optionalDependencies`. The committed `package-lock.json`'s `packages` map contained only 13 of those 15 entries — critically missing `@rolldown/binding-linux-x64-gnu`, the exact package a standard Ubuntu GitHub Actions runner needs, and also missing `@rolldown/binding-darwin-arm64` (the local dev machine is Intel/`darwin-x64`, per ADR-019, so this gap was invisible locally). `npm ci` correctly refuses to fabricate a missing optional-dependency lockfile entry, so it failed on the Linux runner while succeeding locally.

**Root cause:** the lockfile had, at some earlier point, been regenerated with `npm install` run on top of an already-partially-populated `node_modules/` rather than a clean slate. npm's lockfile writer narrows the *written* optional-dependency entries to what it can resolve against the current install state in that situation, rather than the package's full declared multi-platform set — silently dropping platform variants nothing local happened to need. This is not the previously-cited `npm/cli#4828` optional-dependency-omission bug manifesting identically; it is a related, narrower completeness gap with the same practical symptom (a missing optional platform entry breaking `npm ci` on a different platform).

**The fix:** `rm -rf node_modules package-lock.json && npm install` (a genuinely clean regeneration, not `--package-lock-only` against an existing `node_modules/`, which was verified to reproduce the *same* narrowed, incomplete result). This restored all 15 rolldown platform-binding entries to `package-lock.json`, including `linux-x64-gnu`. Verified directly, not assumed: `rm -rf node_modules && npm ci` against the corrected lockfile installs cleanly and reproducibly; `npm run typecheck`, `npm run build`, `npm run test:core` (358/358), and `npm run test:ui` (242/242) all pass unchanged afterward. Three transitive patch-level versions moved as an incidental side effect of time passing under existing caret ranges (`postcss` 8.5.26→8.5.28, `tinyspy` 4.0.4→4.0.6, `fsevents` 2.3.3→2.3.2 — the last is macOS-only and irrelevant to Linux CI) — no directly-depended-on package's version, and no rolldown version, changed. The CI workflow's install step now runs plain `npm ci` against the corrected, committed lockfile — no lockfile deletion, no re-resolution, no workaround — and a new step prints `node --version`/`npm --version`/`npm ls @playwright/test`/`npx playwright --version` so the actual resolved toolchain for any given run is always captured, closing the "actual remote Playwright version could not be proven" gap ADR-019 also recorded.

**Explicitly rejected:** adding `@rolldown/binding-linux-x64-gnu` (or any platform-native package) as a direct root dependency merely to force it into the lockfile. That would misrepresent an optional, platform-conditional transitive dependency as a required direct one, and would not address the actual root cause (lockfile completeness) — it would only mask this specific symptom while leaving the same class of gap free to recur for any other optional multi-platform package. No package manager change, no Vite major-version change, and no Node major-version change was needed or made.

**Governance effect:** if `package-lock.json` is ever regenerated by hand (rather than through routine `npm install`/`npm update` on an already-consistent tree), regenerate it from a clean `node_modules/` (`rm -rf node_modules` first), not on top of a partially-populated one — and verify optional multi-platform dependencies (rolldown, esbuild-style native binaries, etc.) retain their full declared platform set in the resulting lock before committing. CI dependency installation must always be a plain `npm ci` against the committed lockfile; reintroducing a lockfile-deleting or re-resolving workaround requires a new governance decision, not a routine CI edit.

## ADR-023 — Post-Audit Runtime Hardening

**Status:** Accepted

**Context and finding disposition:** An external audit issued a conditional pass with four remediations after the immutable FSG-006 candidate had been certified. Source inspection confirmed a concrete target-size Blob-retention issue and a plausible low-alpha quality concern. It also corrected two audit characterizations: cancellation already hard-terminates the worker without waiting for HEIC/WASM to yield, and HEIC WASM is already a Vite-emitted same-origin asset rather than an arbitrary remote binary.

**Memory remediation:** ADR-015's search order, bounds, dimension tiers, and outcomes remain unchanged. Quality-probe history now stores only `quality` and `byteSize`; losing max/min/midpoint Blob values leave their decision scope; only the selected fitting candidate retains a Blob. Cross-tier `closestMiss` is metadata-only. Existing canvas zeroing before tier replacement and in `finally`, plus final `ImageBitmap.close()`, remain authoritative. Deterministic ownership tests and repeated browser jobs prove the reference graph and continued operation, not garbage-collector timing or a physical-device memory ceiling.

**HEIC cancellation:** No timeout or `AbortController` is added. `cancelImageJob()` may post `CANCEL_JOB`, then immediately settles cancelled; `finish()` detaches every worker handler and calls `terminate()`. A fake worker that never handles any message proves late results cannot change the outcome and the next job uses a fresh worker. Browser HEIC cancellation/recovery exercises the same host path.

**Halo decision:** NO ALGORITHM CHANGE JUSTIFIED. A deterministic matrix compared the certified `alpha > 0.05` unblend baseline, a `>= 0.20` threshold, and the proposed `0.20` denominator clamp across three color pairs, four edge/stroke shapes, five nearest 8-bit alpha samples, and light/dark composites. Baseline maximum visible channel error was 1, versus 33 for the threshold and 13 for the clamp; both alternatives caused unacceptable foreground-color damage. The audit's erosion/falloff proposal is NOT IMPLEMENTABLE AS SPECIFIED because it supplied no exact mathematical policy. The experimental clamp was removed and existing thin-stroke/curve/browser-preview behavior retained.

**CSP and headers:** Built responses use `default-src 'self'; script-src 'self' 'wasm-unsafe-eval'; style-src 'self'; img-src 'self' blob:; font-src 'self'; connect-src 'self'; worker-src 'self'; object-src 'none'; base-uri 'none'; form-action 'self'; frame-ancestors 'none'`, plus `nosniff`, `strict-origin-when-cross-origin`, and a camera/microphone/geolocation-denying Permissions Policy. Neither `'unsafe-eval'` nor `'unsafe-inline'` is allowed. The narrow WASM permission is required for the explicit `WebAssembly.compile()` call. HSTS is owned by the HTTPS edge because Laravel does not terminate TLS. Laravel Boost's development-only injected logger is disabled only in production browser certification; development HMR/logger behavior is not treated as a production CSP requirement.

**WASM integrity decision:** Retain exact `@discourse/heic@1.0.0` plus `package-lock.json` SHA-512 integrity and reproducible `npm ci` as the selected control. This mitigates registry/tarball mutation during install; the emitted content-hashed same-origin filename also prevents accidental asset mismatch. A second build-time SHA-256 check would detect only a narrow post-install mutation and can be bypassed by a compromised build environment that changes the check. Vendoring adds patch/provenance maintenance and still trusts the repository/build. A runtime digest adds fetch/CPU complexity and, because the verifier is the same JavaScript execution context, does not protect against compromised origin JavaScript or XSS. None of the four options alone protects a compromised build host or origin; those require CI/deployment integrity and XSS prevention. The installed and emitted WASM both measured SHA-256 `832bfb37148038257e56216d165cfae24a8afaa7cae8fc0ddb1ef4bf495612a9`, recorded as evidence rather than a second enforcement system.

**Residual limitation:** The external constrained-iOS OOM claim supplied no reproducible device/version/fixture/memory record available to this environment. Its state is **EXTERNAL AUDIT CLAIM — NOT LOCALLY REPRODUCED**. The independently demonstrable reference-lifetime improvement is implemented regardless; no claim of a physical-iOS fix is made.

**Governance effect:** FSG-006 remains historically closed at its certified checkpoint. FSG-006R is a post-audit hardening gate; FSG-007 stays paused until Product Office accepts its final report, and FSG-008 remains not started.

## ADR-024 — FSG-007 logo readiness: source-resolution transparent master and automatic outer-canvas trim

**Status:** Accepted

**Why:** A transparent logo surrounded by its uploaded document dimensions is not website-ready. It creates unusable header/footer spacing and conceals the artwork's real useful resolution. Logo Pack therefore prepares the accepted transparent master around meaningful logo content before deriving the governed seven outputs. This is a Logo Pack preparation rule under ADR-007's explicit/preset exception; it is not a universal image auto-crop and it does not alter internal negative space.

**Analysis and output resolution are separate:** background classification/removal remains bounded at `TRANSPARENT_MASTER_MAX_DIMENSION = 1024`. The accepted removal model is then applied to the orientation-normalized source-resolution canvas in RGBA strips bounded to approximately 8 MiB each. The original source RGB supplies final detail; the bounded raster supplies connected-background/edge decisions; both passes share the exact same edge-ramp/decontamination primitive. Already-transparent sources bypass removal and retain their source pixels directly. This supersedes ADR-020 only where it described the 1024px analysis raster as the final downloadable master; ADR-020's removal policy, verification states, and preview-before-package contract remain unchanged.

**Outer-alpha bounds:** `MIN_MEANINGFUL_ALPHA = 1`, independent from background-removal thresholds, preserves the faintest representable anti-aliased perimeter. Bounds include disconnected opaque pixels (punctuation, letter dots, trademarks, separate marks) and all connected partial-alpha strokes. Only an isolated pixel at alpha `<= 16` is ignored as barely-visible residual contamination; there is no general connected-component deletion. A result also needs accumulated alpha mass of at least `16` opaque-pixel equivalents or it is `failed` as `insufficient-visible-content`, never cropped to a meaningless ready file.

**Safe padding:** padding is `round(3% × shorter visible dimension)`, clamped to `2–24 px`, added outside the detected bounds on a new transparent canvas. The content rectangle is copied 1:1; `foregroundRescaled` is always false. `canvasTrimmed` reports outer-canvas removal separately from transparency and resolution status.

**Logo Pack derivation and product truth:** Transparent-mode packaging receives the full-resolution, verified/needs-review, trimmed master Blob. Header outputs retain artwork proportions through the existing max-bound resize rules. ICO/favicon/app-icon outputs retain ADR-018's intentional square canvases and `ICON_CONTENT_SCALE`; their controlled whitespace is not accidental source canvas. The exact seven-file contract and filenames do not change. The UI reports Original, Prepared logo, Transparency, Canvas, and Resolution as separate facts; low useful artwork resolution remains a warning and is never upscaled into a claim of recovered detail.

**Safety and lifecycle:** the existing 24 MP preflight ceiling remains the outer source-resolution bound, only one heavy worker job may run, strip checkpoints remain cancellable, the decoded bitmap is closed, and source/analysis/output canvases are zeroed in `finally`. Full-resolution preparation necessarily has a larger canvas footprint than ADR-020's former analysis-sized export; it does not remove or weaken the global decode limit.

## ADR-027 — FSG-007 enclosed-background transparency remediation

**Status:** Accepted

**Defect and source finding:** Realistic logo evidence proved that ADR-020's boundary-seeded flood could remove the source background while leaving an identical background-coloured region opaque when foreground topology enclosed it. Letter counters and ring interiors were unreachable from the image border by design. The worker could nevertheless return `verified` because its checks proved alpha presence, foreground viability, border confidence, and encoded-PNG validity, but did not account for material enclosed source-background regions.

**Targeted second pass, not global colour removal:** `removeConnectedBackground()` retains the existing inferred border-median background model and Gentle/Balanced/Strong thresholds. After the boundary flood, it labels remaining background-like components on the bounded analysis raster. A component is cleared only when deterministic size, aspect, fill, compactness, and colour-core evidence make it counter-like. The implementation never removes pixels because they are white or bright; every comparison is against the inferred source background.

**Ambiguity is preserved and surfaced:** Thin, irregular, similar-but-not-exact, or otherwise uncertain regions remain foreground and contribute to `ambiguousEnclosedBackgroundRatio`. That metric makes `verified` impossible and produces `needs-review` with `ambiguous-enclosed-background`. This protects intentional white/light strokes and highlights that match the source canvas. A 4-pixel analysis component is the minimum material region considered; confident removal additionally requires at least 8 pixels or 0.0008% of the bounded raster, whichever is larger, dimensions of at least 3×3, aspect ratio at least 0.5, fill at least 0.4, bounded compactness, and near-exact source-background evidence. These are topology/quality guards, not semantic logo recognition.

**Analysis/source-resolution bridge:** Downsampling can blend a small counter's pure background core into surrounding type. Compact analysis components that satisfy the topology rules but lack near-exact analysis colour are marked for source-resolution confirmation rather than deleted or ignored. The existing strip-bounded source-resolution pass clears only pixels with an exact/near-exact source-background core and applies the governed edge decontamination around that confirmed core. Similar-but-not-exact light artwork remains unchanged. Protected ambiguity has priority over this projection. Final RGB/detail still comes from the source-resolution raster; no mask raster is enlarged and substituted for the source.

**Inner-edge and lifecycle guarantees:** Accepted exterior and enclosed regions use the same soft-alpha/RGB-decontamination primitive. The analysis pass remains capped at 1024px, uses bounded typed masks plus one reused iterative queue, and the source pass remains strip-bounded and cancellable. ADR-024's full-resolution master, outer-alpha trim, safe padding, already-transparent bypass, and no-rescale contract are unchanged. Keep Existing Background does not enter this pipeline.

**Logo Pack contract:** The corrected accepted master continues to feed header assets, while the explicit ADR-025/ADR-026 favicon source feeds square outputs. The ZIP remains exactly seven files. No UI, modal, favicon-selection, worker-concurrency, HEIC/WASM, target-size, CSP, SEO, or ProductFamily behavior changes under this remediation.

**Governance effect:** ADR-020 remains authoritative for background inference, strength modes, preview, and tri-state readiness, but its boundary-only removal description is superseded by this conservative enclosed-region pass. `verified` now means no known material enclosed source-background ambiguity remains; uncertainty is an explicit review state, not a clean-success claim.

## ADR-028 — FSG-007-FIT-002 Guided Fit exact destination geometry

**Status:** Accepted

**Foundation this extends:** FSG-007-FIT-001 introduced an exact-frame processing path for Quick Fit's manual form — a `maxWidth`/`maxHeight` pair could mean an EXACT output frame (never a bounding box), with a user-approved crop required whenever the source's aspect ratio didn't already match, and explicit approval required before any upscale beyond the source's own detail. That path (`packages/core`'s `ExactDimensionsOptions`, `isCropRequired`/`largestCenteredCropForRatio`, and the worker's own enforcement in `process-image.ts`) was never previously recorded here; this ADR records it retroactively as the foundation FIT-002 builds on, rather than presenting FIT-002 as inventing crop/exact-frame handling from nothing.

**Why:** Guided Fit's Hero/Content/Card presets originally compiled to aspect-preserving bounding boxes — a source was scaled to fit within a maximum width/height, never cropped, and its actual output aspect ratio was whatever the source happened to have. This meant two different sources chosen for the same destination (e.g. "Hero") could produce meaningfully different-shaped results, undermining the premise that a destination preset describes a real, consistent placement. Hero/Content/Card now compile to an EXACT destination frame — Hero 1600×900 (16:9), Content 1200×800 (3:2), Card 800×600 (4:3) — each preserving its existing governed byte target and format (500 KB/300 KB/150 KB, WebP) from before this change; only geometry changed.

**FileSetGo's own recommendation, not universal web law:** As with every preset in `PRESET_CATALOG` (`provenance.kind: 'filesetgo-recommended'`), these three exact sizes are FileSetGo's own practical guidance for common website placements — not a claim that they are the only correct dimensions for any website's hero/content/card imagery, and not sourced from any external platform requirement.

**Cropping is always user-controlled, never automatic:** Exactly as FIT-001 established for Quick Fit's manual form, Guided Fit never crops a source on its own. Whenever a selected destination's exact aspect ratio doesn't already match the source (beyond the shared 0.5% tolerance in `isCropRequired`), the user is shown the crop stage and must explicitly confirm a frame before processing can proceed — never inferred, never automatic, never AI-selected.

**No new crop implementation:** Guided Fit's crop step reuses the exact same interactive locked-ratio crop engine Quick Fit's manual form already used — extracted into one shared module (`resources/js/quick-fit/locked-crop-stage.ts`) instantiated twice, once per dialog, against each dialog's own markup — rather than a second, copy-pasted implementation. The two dialogs can never silently diverge in crop behavior. The small approval-gating predicate (crop-required-and-unconfirmed / upscale-required-and-unapproved) was similarly extracted into one shared `checkGeometryApproval()` (`resources/js/quick-fit/crop.ts`), called identically by Quick Fit's form validation and Guided Fit's preset runner.

**No silent upscale, no silent shrink-to-hit-byte-target:** When reaching a destination's exact frame requires enlarging beyond the (possibly cropped) source's own resolution, Guided Fit requires the same explicit upscale approval Quick Fit's manual form requires — never silent. Symmetrically, every `exactDimensions` preset is validated (`validate-preset.ts`) to require `dimensionPolicy: 'hard'`: the governed byte target is met by quality/format search alone, at the fixed exact frame: the frame itself is never silently shrunk to reach a byte target.

**Crop/upscale approval is destination- and source-specific, never carried over:** `GuidedFitController` clears any confirmed crop and upscale approval on every destination switch (even reselecting the same destination) and on every source replacement or reset. A crop confirmed for one destination is never silently reused for a different one, or for a replacement source file.

**Already-ready semantics changed from bounding to exact:** Because the destination is now a fixed frame rather than an upper bound, "this file already fits this recommendation" (`evaluateAlreadyReady`) now requires the source to be at the EXACT governed width and height (as well as format and byte budget) — a source smaller than the frame is no more "ready" than one that's larger, since neither is the exact size FileSetGo would otherwise produce.

**Result metadata is always the actual output:** The GO panel's dimensions/format/size for a Guided Fit result were already, and remain, read directly from the real processed Blob's own metadata (`QuickFitWorkflow.settleSuccess()`) — never the requested target figures echoed back. This was already true generically for every Quick Fit/Guided Fit result before this milestone and needed no change to remain true for the new exact-frame path.

## ADR-029 — FSG-007-FIT-003 shared processing-transition and atomic Ready → GO handoff

**Status:** Accepted

**Why:** Quick Fit, Guided Fit, and Logo Pack each finished a job by silently, immediately closing their task dialog the instant the underlying job resolved to `'success'` — with no in-modal acknowledgement that real work happened, and no structural guarantee that the modal closing and the shared "GO" result panel populating happened together (it worked only by accident of synchronous code ordering). This introduces one shared `Preparing → Validating → Ready` transition, and a genuine atomic handoff, reused identically by all three tools rather than three separate implementations.

**No `packages/core` changes were needed:** the worker already performs real, awaited output validation before resolving success — `validateOutput()` (`packages/core/src/workers/process-image.ts`) genuinely re-decodes and re-checks the produced Blob inside the existing `'finalizing'` stage window for single-image jobs, and Logo Pack's own per-asset validation already happens inside `'encoding'` for image-set jobs. Labeling `'finalizing'` as "Checking the finished file" (single-image jobs) is therefore truthful without inventing a new stage; Logo Pack, whose real validation moment doesn't correspond to any single stage the same way, is labeled per its own real stages (`'encoding'`, `'packaging'`) instead of claiming a "validating" beat it doesn't have. This mirrors FIT-002's own "zero core changes" precedent.

**One shared reveal gate, not three one-shot booleans:** `resources/js/shared/reveal-gate.ts`'s `RevealGate` generalizes the one-shot `guidedFitAutoClosedForSuccess` boolean FIT-002 introduced into the single mechanism behind every tool's atomic handoff — Quick Fit and Guided Fit share one instance (they read the same underlying `QuickFitState` and only one of their two dialogs is ever open at a time); Logo Pack, with its own independent state, gets its own. `resources/js/shared/processing-phase.ts` derives one `ProcessingPhase` (`idle|preparing|validating|ready|failed|cancelled`) from each tool's existing, unmodified state union — never a restructuring of `QuickFitState`/`LogoPackState`.

**Atomicity is structural, not timing-based:** GO's own DOM is populated unconditionally the instant the real result exists (before the perceptible ~350ms Ready beat even begins) — the gate's timer governs only when the dialog closes and the status bar/live-region announce "success", never whether the job is done or what text is shown. There is therefore no code path where the modal closes while GO is still empty. The ~350ms tolerance exists solely to make the Ready beat perceptible (never to fake computation) and collapses to effectively instant under `prefers-reduced-motion`.

**Genuine job cancellation is unaffected:** cancellation continues to hard-terminate the worker exactly as ADR-023 established — this milestone adds no new cancellation plumbing, only a truthful in-modal display of the cancelled outcome and (for Quick Fit) an automatic return to the editable requirements step on cancel, matching the pre-existing certification that a cancelled job can be resubmitted immediately with no extra "Back" click.

**No new runtime dependency:** the shared FILE→SET→GO glyph (`<x-processing-glyph>`) is plain inline SVG + CSS (`.fsg-processing-glyph*` in `app.css`), extending the existing hand-drawn `<x-icon>` convention — opacity/transition only, no canvas, no animation loop, and a reduced-motion override that collapses it to a static end state.

## ADR-030 — FSG-007-FIT-003-R1/R2/R3 processing-state truth, perceptibility floor, and full-page transition

**Status:** Accepted

**Why:** Three successive Product Office directives corrected ADR-029's initial implementation, each addressing a distinct defect discovered only once the transition was actually observed running: (R1) the eyebrow/title/status text could visually disagree with each other or with the real phase, and Change Image/header-close were disabled rather than hidden during active work; (R2) a real screen recording showed the transition lasting only ~0.20–0.30s — structurally correct but not perceptible to an actual user; (R3) processing was happening inside a task modal at all, when the Product Office judged it should be a full-page, application-level transition that locks the entire workspace, not a modal-scoped one. All three corrections reuse ADR-029's architecture unchanged; none required a fourth rewrite of the underlying state machine.

**R1 — one shared rendering rule, hide don't disable:** `resources/js/shared/render-processing-section.ts` restructures each tool's copy into one `ProcessingCopy` shape (`preparing`/`validating`/`ready`/`failed`/`cancelled`, each producing a matched `{eyebrow, title, status}` triple) so eyebrow/title/status can never independently drift out of agreement with the real `ProcessingPhase` or with each other — there is exactly one function (`resolveProcessingStateText`) that derives all three strings from one phase value. Change Image and the header `×` are hidden (`.hidden`, removed from layout and the accessibility tree) rather than merely `disabled` while `isDialogActivelyProcessing()` is true, so the workspace never shows a control that looks clickable but silently does nothing.

**R2 — a minimum visible-dwell floor, measured from real paint, that never stacks:** real elapsed time from confirm-click to modal-close could be as short as ~200ms for a fast job — correct, but imperceptible. `resources/js/shared/minimum-dwell-gate.ts`'s `MinimumDwellGate` fixes this without faking any work: `markVisible()` uses a double-`requestAnimationFrame` to confirm the Preparing/Validating state has actually painted (not merely been requested) before starting its clock, and `armIfNeeded()` waits only the *positive remainder* of the governed minimum — a job that is already naturally slower than the floor waits zero additional time, so slow jobs are never penalized with a stacked floor on top of their own real duration. `applyMinimumDwell()` in `controller.ts` composes this with the existing `ProcessingPhase`/`RevealGate` machinery from ADR-029 by displaying the last real active phase (never a fabricated one) while the floor's remainder elapses. Two independent constants govern the two distinct dwell beats — `MIN_PREPARING_VISIBLE_MS` (minimum time Preparing/Validating must be visible) and `READY_DWELL_MS` (ADR-029's own Ready beat, governing the atomic close) — both were raised once more (700→800ms, 400→500ms) after direct, confirmed user feedback that the transition was still too fast to reliably perceive; this is a timing-constant change only, with no architectural implication.

**R3 — the transition is application-level, not modal-level:** the task dialog's job now ends at final user confirmation; it closes immediately, and a single full-page overlay (`#fsg-processing-overlay`, a plain `<div>` — not a `<dialog>`, not a route, not a second result page) takes over, covering the header/nav/workspace and marking everything else `inert` (`setWorkspaceInert()`) for the duration. This is a presentation-layer relocation only: the overlay reuses `ProcessingPhase`, `RevealGate`, `MinimumDwellGate`, the processing glyph, and cancellation exactly as ADR-029/this ADR's R1/R2 sections established — one shared overlay renders task-aware copy for all three tools (`guidedFitProcessingCopy(preset)` joins the existing Quick Fit/Logo Pack copy tables) rather than three separate overlays. The overlay markup lives in a new `@stack('overlays')` in the shared layout, as a direct sibling of `<main>`/nav/footer at the `<body>` level — deliberately not nested inside `<main>` or any dialog, since `setWorkspaceInert()`'s `inert`-marking walks `document.body`'s direct children and would otherwise make the overlay inert along with everything else it's supposed to leave interactive. Cancel is shown on the overlay only while the underlying job is genuinely still running (never during the post-completion Ready dwell, which is presentation-only). The old in-modal processing-rendering code from R1 (each dialog's own processing section, and its own `RevealGate`/`MinimumDwellGate` arming calls) is deliberately left in place rather than removed: it is now ~~invisible (dialogs close before it would render)~~ — **this specific claim is factually wrong and is superseded below; do not treat it as current architecture** — but still the structural home of the atomic-handoff arming logic, so removing it was judged higher-risk than leaving it as known, disclosed dead-but-necessary code.

**Correction (ADR-031) — SUPERSEDES the claim directly above:** the claim in the previous paragraph — that the old in-modal processing markup was "invisible (dialogs close before it would render)" — was factually wrong and must not be read as describing current behavior. A measured recovery audit proved the animated `closeWorkflowDialog()` exit left the `<dialog>` genuinely `open` (and therefore still painting in the browser's top layer, above this section's own ordinary-stacking overlay div, regardless of z-index) for up to ~250ms after confirmation, during which the old in-modal pane was in fact visible — a real top-layer overlap R3 had incorrectly declared impossible. ADR-031 (immediately below) replaces the animated close with a synchronous one and then deletes the old in-modal processing markup outright, closing the gap for good. This paragraph's architecture claim (one shared overlay, reused `ProcessingPhase`/`RevealGate`/`MinimumDwellGate` primitives, no `packages/core` changes) remains accurate; only the "invisible" assertion is retracted. **Current architecture is ADR-031's, not this paragraph's dead-code assumption** — see ADR-031's "old in-modal processing presentations were removed, not merely re-hidden" for what actually ships.

**No `packages/core` changes, no new cancellation plumbing, no new runtime dependency across any of R1/R2/R3** — every requirement was satisfiable by composing already-existing, already-tested primitives at the presentation layer, consistent with ADR-029's original "zero core changes" finding.

## ADR-031 — FSG-007-FIT-003-R4 first-class processing interstitial and the synchronous processing-handoff close

**Status:** Accepted

**Why:** A dedicated recovery/verification pass (not routine development) measured the exact defect ADR-030's R3 section had incorrectly declared solved: instrumenting the live app with a `MutationObserver`/rAF sampler showed the task `<dialog>` remaining genuinely `open` — and therefore still painting in the browser's top layer, above the ordinary-stacking `#fsg-processing-overlay` div regardless of z-index — for up to ~250ms after the user confirmed, because the processing handoff reused `closeWorkflowDialog()`'s 160ms animated exit (`.is-closing` + deferred `.close()`), the same path correctly used for ordinary user dismissal (Close/Escape/backdrop). For that window, the old in-modal "Preparing your file" pane was genuinely visible on top of the new full-page overlay. Separately, the Product Office judged the full-page surface itself — while structurally correct per R3 — too visually minor to read as a genuine File. Set. Go. application state rather than a small loader dropped onto a blank page. This ADR corrects both.

**Canonical principle this milestone establishes:** *Task modals own decisions. The application processing interstitial owns work. The workspace owns results.* Each of the three surfaces has exactly one job, and R4's changes exist to make that boundary real rather than merely intended.

**The fix is a second, distinct close path — not a smaller version of the first:** `closeWorkflowDialogForProcessing()` (`resources/js/quick-fit/controller.ts`) closes the dialog synchronously — no `.is-closing`, no animation, no deferred timer — the instant a run is confirmed, immediately before the full-page overlay can ever open. `closeWorkflowDialog()` itself is unchanged and remains the correct path for ordinary dismissal; the two paths are deliberately not unified, because "close because the user is done deciding and work is starting" and "close because the user dismissed an idle dialog" are different events with different correctness requirements — the first must never race a second surface, the second has no such constraint and benefits from the softer animated exit. Real worker execution is untouched: the job still starts in the same synchronous handler as before, immediately after the dialog closes — this fix changes when the dialog visually leaves, never when real processing begins.

**The old in-modal processing presentations were removed, not merely re-hidden:** per-tool duplicate live processing UIs (Quick Fit's `#quick-fit-step-processing`, Logo Pack's `#logo-pack-step-processing`, and the "processing" branch of Guided Fit's `#guided-fit-step-3` pane) were deleted outright — the type-level `'processing'` dialog-step values, their DOM sections, and their `renderProcessingSection()` calls are gone, not left in place behind a now-true assumption that they won't render. Guided Fit's `#guided-fit-step-3` pane itself is retained (its progress-bar step-numbering and post-run Back-navigation semantics predate this defect and are unrelated to it), but its content branch that mirrored live Preparing/Validating copy was removed; its remaining branches (cancelled/failed/success/default) only ever render on a later reopen of an already-concluded run, never during active processing. A regression proves the fix structurally, not just by absence of a symptom: for each of Quick Fit, Guided Fit, and Logo Pack, an in-page `MutationObserver` installed *before* the run starts captures `dialog.open` for all three dialogs at the exact first moment the overlay becomes visible (`tests/browser/specs/processing-transition.spec.ts`, describe block `FSG-007-FIT-003-R4: no modal/overlay top-layer overlap`) — never a later poll that only proves a dialog *eventually* closes, which is what let the original defect through undetected.

**The interstitial became a genuine top-level application state, not a bigger loader:** the surface now reuses the project's own approved brand mark (the same header/footer logo PNGs, theme-aware, never redrawn) at restrained secondary size; the shared FILE→SET→GO glyph is substantially larger (`fsg-processing-glyph--overlay`); the title is meaningfully larger and scales with viewport width; a one-line, frozen-at-confirmation task-context summary (e.g. `1600 × 900 · WebP · target under 500.0 KB`, `Preparing 7 website-ready logo assets`) ties the transition back to the decision just made in the now-closed dialog; and the ordinary header/footer are hidden outright via a `body.fsg-processing-active` class (not merely occluded by the overlay's own opaque background/z-index, which was the R3 approach). None of this is a route, a new dependency, or a `packages/core` change.

**Perceptibility floor raised again, same non-stacking guarantee:** `MIN_PREPARING_VISIBLE_MS` 800→1200ms, `READY_DWELL_MS` 500→600ms, after direct Product Office feedback that R2/R3's values still read as too fast. The underlying `MinimumDwellGate`/`RevealGate` mechanics are unchanged from ADR-030 — a job already visibly preparing at least this long waits zero additional time; only the two constants moved.

**Atomic handoff gains a real result-focus destination:** on a genuine success reveal (not `'unreachable'`, which also collapses to the same `'idle'` phase but has no new GO result to point to), focus now moves to GO's own `#result-title` heading — not the just-closed dialog's trigger button, which is what `closeProcessingOverlay()`'s own generic restore-focus behavior would otherwise leave focused. A restrained one-shot border-color emphasis (`.fsg-result-object--arrived`, `@keyframes fsg-result-arrival`) accompanies it — no bounce, no confetti, no banner.

**Explicitly deferred, not overlooked:** a cosmetic fade-out transition between the overlay leaving and the workspace becoming visible (directive §25, "~150–250ms") was deliberately not implemented this milestone — delaying the overlay's `hidden` class toggle to allow a real opacity transition would either delay `setWorkspaceInert(false)` (leaving the newly-non-inert result heading briefly unfocusable, since focus cannot land inside an `inert` subtree) or decouple the two, reintroducing exactly the class of race this ADR exists to eliminate. The instant cut this milestone ships with is the same behavior R3 already certified; revisiting it is left to a future milestone with room to solve the focus/inert ordering properly, rather than risk a new timing defect under this one's time pressure.

**FSG-007F remains paused pending this ADR's acceptance** — no `packages/core`, cancellation, Guided Fit geometry/preset, Quick Fit exact-dimensions/crop, or Logo Pack asset-contract changes were made or are implied by this milestone.

## R5 addendum — the FILE → SET → GO processing rail

**Status:** Accepted (extends ADR-031; the architecture ADR-031 froze above — synchronous modal close, `ProcessingPhase`, `RevealGate`, `MinimumDwellGate`, 1200ms/600ms timing, atomic GO population, cancellation, result focus — is unchanged by this addendum in every particular).

**Why:** R4 fixed the architecture (no top-layer overlap, a genuine top-level application state) but the Product Office judged the *visual* result still read as a small loader centered in mostly empty canvas — a technically-full-viewport surface whose visible content cluster remained narrow. This addendum is presentation-only: it replaces the small inline `<x-processing-glyph>` inside the overlay with a substantial three-stage FILE → SET → GO rail. The canonical principle this addendum records:

> FILE / SET / GO is not merely a loading glyph; it is the structural processing grammar of File. Set. Go. — what came in, what's happening, and where the result is heading, given real visual architecture rather than a small icon row.

**Zero new phase logic:** the rail's every state — FILE always "accepted", SET active-then-resolved, GO pending-then-(optionally-checking)-then-resolved — is driven entirely by the same `data-phase` attribute `renderProcessingSection()` (`resources/js/shared/render-processing-section.ts`, byte-for-byte unmodified) already set on one root element. The only JS change was *which* element receives that attribute (`#fsg-processing-rail` instead of the small glyph's root) — a presentational retarget, not a new branch on `ProcessingPhase` anywhere. Every stage/caption/connector visual state is pure CSS keyed off that one attribute value (`[data-phase='preparing']`, `[data-phase='validating']`, `[data-phase='ready']`), using the existing `~=` attribute-selector idiom so one small set of rules covers every caption span without per-phase JS branches.

**GO's "validating/checking" state is never invented:** Logo Pack's `logoPackProcessingPhase` still never returns `'validating'` (unchanged, per ADR-029/030) — the rail's GO-stage "Checking" CSS rules simply never match for that tool, exactly as intended; nothing in the rail special-cases Logo Pack to suppress a state that was never going to render anyway.

**The FILE-stage thumbnail reuses the existing unified-source pipeline, not a new one:** `#fsg-processing-overlay-source-thumb` was added to the same `sourceThumbnailImages` array `renderSourceThumbnails()` (FSG-007-FIT-001B) already writes one shared object URL into — no new source-preview logic, no new lifecycle to manage, and the existing HEIC/no-preview fallback (hide the `<img>`, show a plain file icon) is a pure CSS `:not([src])` rule, not a JS branch.

**Regression note — a real R5-introduced defect caught before landing:** an early draft of `.fsg-processing-overlay`'s CSS set `display: flex` directly on the base rule instead of leaving `display` to the `.hidden`/`.flex` utility toggle already governing it. Same specificity as Tailwind's `.hidden`, later in source order — it made the overlay permanently visible regardless of the `hidden` class, silently covering the homepage the instant the page loaded. This is the exact class of bug `.ai/rules/css.md` already documents (`.fsg-task-dialog__progress li.hidden` vs `li`). It was caught immediately by the existing R3/R4 evidence spec failing loudly (`#quick-fit-open` unreachable, covered by the wrongly-visible overlay) before any commit, fixed by removing the stray `display` declaration, and is recorded here as a reminder that this specific gotcha recurs even with the rule already written down — every new rule touching `.fsg-processing-overlay`'s own selector must be re-checked against it.

**Responsive is three deliberately distinct compositions, not one rail at three scales:** desktop (≥960px) is the full horizontal rail; a `max-width: 959px` tablet band uses the same horizontal grammar at reduced node/type scale; a `max-width: 639px` mobile band switches to a genuine vertical FILE ↓ SET ↓ GO stack using short vertical connectors, per directive §22–§24's explicit rejection of "scale the desktop rail down until everything is tiny."

**Verification:** a new regression (`processing-transition.spec.ts`, describe block `FSG-007-FIT-003-R5: processing visual system has real presence`) asserts the visible rail's own bounding-box width is more than half the 1440px viewport — a relative measurement of the actual rendered child, not an invisible wide parent — plus the full FILE/SET/GO caption story across Preparing and Ready, plus the FILE-stage thumbnail's real `blob:` source. Two pre-existing R3/R4 tests (`Reduced motion`, indirectly `Duplicate submit`) referenced the now-removed `.fsg-processing-glyph` selector inside the overlay and were updated to target the rail's own spinner element — a selector update only, no behavioral change to what either test certifies.

## R5.1 addendum — task context wording matches the real phase, not just the title

**Status:** Accepted (extends the R5 addendum and ADR-029/030/031 above; no phase logic, gate timing, rail structure, or cancellation behavior changes).

**Why:** R1 (ADR-030) guaranteed that eyebrow, title and status can never disagree with each other or with the real `ProcessingPhase`, because all three are derived from one `resolveProcessingStateText` call. Logo Pack's one-line task-context string beneath that triple was outside that guarantee: it was a single value frozen at confirmation (`Preparing 7 website-ready logo assets`) that never changed for the rest of the run, so once the overlay reached Ready — title `Your logo pack is ready`, status `All seven files are checked and ready to download.` — the context line directly beneath them still carried the word "Preparing," contradicting the state it was displayed alongside. This was Logo Pack's own defect, not a shared one: Quick Fit's and Guided Fit's task-context strings (`quickFitTaskContext`, `guidedFitTaskContext`) are phase-neutral requirement summaries (dimensions/format/target byte budget) with no active verb to begin with, so they were correctly left untouched.

**Fix scope, one function, one call site:** `logoPackTaskContext(phase: ProcessingPhase)` (`resources/js/quick-fit/controller.ts`) now takes the same `ProcessingPhase` value the overlay's eyebrow/title/status already read, and returns `'Preparing 7 website-ready logo assets'` while `phase.kind !== 'ready'`, or the static `'7 website-ready logo assets'` once `phase.kind === 'ready'`. The pack's asset count remains the fixed, governed constant it always was (ADR-018's seven-file contract) — this addendum changes only which verb-bearing sentence wraps that count, never the count itself or how it's computed.

**No new state, no new gate:** the call site simply passes the phase value through at render time instead of caching a string once at confirmation; `ProcessingPhase`, `RevealGate` and `MinimumDwellGate` are unchanged, and no new branch was added to any of them.

**Verification:** `processing-transition.spec.ts`, describe block `FSG-007-FIT-003-R5.1: task context never carries active wording into Ready` — Logo Pack's context is asserted literally equal to the Preparing string while active, then asserted to no longer contain "Preparing" while still matching the asset count once Ready; Quick Fit/Guided Fit's context is asserted byte-identical before and after the transition, proving their phase-neutrality is unaffected; a carried-over dark-mode assertion on the GO checkmark's rendered color closes out the same describe block.
