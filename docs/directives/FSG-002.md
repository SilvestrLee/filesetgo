# 1. Milestone Objective

Build the deterministic target-file-size engine used by future FileSetGo
workflows.

The engine must accept:

- a valid input image;
- a requested output format;
- a target maximum byte size;
- dimension constraints;
- a dimension policy;

and return either:

1. a valid locally processed image whose final encoded size is within the
   requested limit; or
2. a structured, deterministic explanation that the target could not be
   achieved within the permitted quality and dimension constraints.

Core concept:

Input
→ Preflight
→ Decode
→ Normalize
→ Candidate dimensions
→ Bounded quality search
→ Output validation
→ Target-size decision
→ Local Blob

The engine must always terminate.

---

# 2. Product Principle

FSG-002 must optimize for:

"Meet the destination requirement while preserving as much image quality
and useful resolution as possible."

It must NOT optimize simply for the smallest possible file.

Priority order:

1. Respect safety constraints.
2. Respect hard dimensions.
3. Meet target bytes.
4. Preserve dimensions where possible.
5. Preserve quality where possible.
6. Never loop indefinitely.
7. Return a useful explanation when the requirement is impossible.

The algorithm must be deterministic for the same input, options, runtime,
and encoder behavior.

# 6. Target Size Contract

Introduce a clear public core contract for target-size processing.

Conceptually:

    targetBytes,
    outputFormat,
    dimensions,
    dimensionPolicy,
    qualityRange,
    onProgress,
})

Do not use this exact signature blindly if a better type arrangement fits
the existing architecture.

The API must expose structured input and structured result types.

Required target-size inputs include:

- targetBytes
- outputFormat
- dimension constraints
- dimensionPolicy
- optional quality bounds where allowed by governance

Default quality bounds:

minimum quality: 0.60
maximum quality: 0.95

Do not silently go below 0.60.

Do not silently exceed 0.95 as part of the target-size search.

If a lossless format does not expose a meaningful quality search parameter,
do not fake one.

# 7. Dimension Policies

Implement two explicit dimension policies.

## HARD

The requested dimensions are authoritative.

The engine may vary encoder quality within the bounded quality range.

The engine MUST NOT reduce dimensions merely to hit target bytes.

If the file cannot meet targetBytes at the minimum permitted quality:

return a structured "target unreachable under hard dimensions" outcome.

Do not silently violate the requested dimensions.

## FLEXIBLE

The requested dimensions are the preferred maximum dimensions.

The engine first attempts to meet targetBytes without reducing dimensions
below the initial candidate.

If quality search cannot achieve the target, the engine may progressively
reduce pixel dimensions.

Each dimension tier should reduce dimensions by approximately 15% while
preserving aspect ratio.

Suggested scale:

nextWidth  = floor(currentWidth  * 0.85)
nextHeight = floor(currentHeight * 0.85)

Use one authoritative helper rather than scattering this math.

Do not upscale.

Do not violate the 24 MP cap.

---

# 8. Quality Search

For lossy JPEG and WebP target-size searches, implement bounded quality
probing.

Authoritative quality range:

0.60 to 0.95

Maximum probes per dimension tier:

5

The algorithm must never perform an unbounded or open-ended quality loop.

A reasonable search strategy is bounded binary-style probing, but the
implementation should optimize for finding the highest usable quality
whose encoded output is <= targetBytes.

Important:

The goal is NOT "find the mathematically exact byte count."

The goal is:

"Find the best quality candidate within the target limit using a strictly
bounded number of encodes."

Do not perform more than 5 quality probes at one dimension tier.

Record every probe internally as structured candidate information so the
engine can deterministically choose the best valid result.

---

# 9. Candidate Selection

At a given dimension tier:

- encode candidate quality;
- validate output;
- record blob size;
- classify candidate as over target or within target.

Among candidates <= targetBytes, select the candidate with the highest
quality.

Do not select a lower-quality candidate when a higher tested quality also
meets the target.

If no quality candidate at the current dimensions meets the target:

HARD:
→ stop with target-unreachable result.

FLEXIBLE:
→ reduce dimensions and retry using another bounded tier.

---

# 10. Dimension-Tier Bound

Flexible dimension reduction must also be bounded.

Do not allow indefinite:

resize
→ encode
→ resize
→ encode

cycles.

Define an explicit maximum dimension-tier count.

Choose a conservative bound based on the 0.85 scale factor and expected
web-image use cases.

Document the chosen number and rationale in the directive implementation
report.

The engine must also stop before dimensions become meaningless.

Introduce explicit minimum output dimensions / minimum useful pixel area
or another deterministic floor.

Do not silently generate a tiny unusable image merely to satisfy an
unreasonable byte target.

If the minimum permitted dimension floor is reached and targetBytes still
cannot be met:

return a structured target-unreachable result.

---

# 11. PNG Behavior

PNG is lossless.

Do not pretend PNG encoder "quality" works like JPEG/WebP.

For PNG target-size requests:

HARD dimensions:

- encode at the requested dimensions;
- validate;
- if <= targetBytes → success;
- otherwise → target unreachable under hard dimensions.

FLEXIBLE dimensions:

- encode;
- if over target, reduce dimensions using the bounded dimension-tier
  strategy;
- retry until target is met or the tier/floor limit is reached.

Do not add a lossy PNG strategy.

Do not introduce color quantization in FSG-002 unless separately approved.

# 14. Worker-First Rule

All repeated encode/resize work must remain inside the worker.

The main thread must not perform:

- pixel iteration;
- repeated canvas encoding;
- quality probing;
- dimension-tier processing.

The host/UI layer may:

- start;
- cancel;
- display progress;
- receive final result;
- receive structured failure.

---

# 15. One Heavy Job

Retain:

MAX_ACTIVE_HEAVY_JOBS = 1

Target-size processing may perform multiple internal encodes, but that is
still ONE FileSetGo heavy job.

Starting a replacement job must cancel/terminate the previous heavy job
under the existing runtime semantics.

---

# 16. Cancellation

Cancellation must be checked:

- before decode;
- after decode;
- before each quality probe;
- after each quality probe;
- before a dimension-tier transition;
- after resize;
- before final result publication.

Hard worker termination remains the backstop.

A cancelled target-size search must never later return a stale success.

# 19. Structured Unreachable Outcome

Do not treat every failure to hit targetBytes as a generic runtime error.

A valid file and functioning runtime may still face an impossible user
constraint.

Model this as a deterministic product/processing outcome.

Examples:

TARGET_UNREACHABLE_HARD_DIMENSIONS
TARGET_UNREACHABLE_MIN_QUALITY
TARGET_UNREACHABLE_MIN_DIMENSIONS

You may choose better names, but preserve the semantic distinction between:

- actual runtime failure; and
- valid optimization search that cannot satisfy the requested constraint.

This is important for FSG-003 UX.

# 20. Target Validation

Validate targetBytes before processing.

Reject:

- zero;
- negative;
- NaN/non-finite;
- malformed values;
- values outside any explicit engine-supported target range.

Do not allow arbitrary numbers to trigger excessive work.

Define a sensible initial minimum target size.

Do not impose a maximum target smaller than the existing source-file cap
without a product reason.

Document chosen target validation limits.

---

# 21. Quality Validation

Reject malformed quality configuration.

Requirements:

0 <= minQuality <= maxQuality <= 1

Project defaults remain:

minQuality = 0.60
maxQuality = 0.95

If custom bounds are permitted by the internal API, they must remain
explicit and validated.

Future public UI does not necessarily need to expose them.

---

# 22. Aspect Ratio

Dimension reduction must preserve aspect ratio.

Do not independently shrink width and height by unrelated values.

Use the normalized raster dimensions after EXIF/HEIF orientation handling.

All final dimensions must be positive integers.

---

# 23. No Upscale

Target-size processing must never upscale by default.

A smaller source should remain smaller unless an explicitly authorized
future workflow asks for enlargement.

Do not upscale merely because destination dimensions are larger.

---

# 24. Output Validation

Every candidate considered for final return must still pass existing
output validation.

At minimum confirm:

- non-empty Blob;
- expected MIME;
- binary signature matches;
- decoded/preflight dimensions match;
- final bytes are known;
- final bytes <= targetBytes before success is returned.

Do not return a candidate based solely on Blob.type.

---

# 25. Encoder Non-Monotonicity

Do not assume browser encoder byte size is perfectly monotonic with quality
for every image.

The bounded search should tolerate occasional non-monotonic results.

Candidate selection must use actually measured encoded byte sizes rather
than assuming a theoretical ordering.

This is another reason to retain all tested candidates within the bounded
probe set and choose the best valid result from observed evidence.

---

# 26. Deterministic Termination

The algorithm must have explicit finite bounds.

For every target-size job, total work must be bounded by something of the
form:

dimensionTierCount × maximumQualityProbes

plus a small constant number of required encodes.

Document the actual maximum possible number of encode attempts for:

- JPEG HARD
- JPEG FLEXIBLE
- WebP HARD
- WebP FLEXIBLE
- PNG HARD
- PNG FLEXIBLE

Do not leave the complexity implicit.

---

# 27. Memory Discipline

Do not retain every candidate Blob indefinitely.

Keep only the candidate metadata needed for search plus the current best
valid Blob.

Release superseded Blob references as soon as practical.

Do not retain multiple full-resolution canvases.

Reuse or reset canvas resources safely where feasible.

Preserve FSG-001 cleanup behavior.

---

# 28. Security / Privacy

No source or generated image may leave the device.

No remote compression service.

No server fallback.

No analytics payload containing:

- source bytes;
- generated bytes;
- filename;
- EXIF;
- image content.

Audit processing code for network APIs after implementation.

The existing same-origin HEIC WASM fetch remains permitted.

No new network path should be required for target-size optimization.
