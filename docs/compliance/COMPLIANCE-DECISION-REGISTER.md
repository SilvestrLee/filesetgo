## 9. Heavy real-processing browser tests: ROOT CAUSE FOUND — Playwright tracing overhead, not a product defect

**Status: RESOLVED (root cause identified with direct causal proof) — no code fix applied (none needed in product code); an infrastructure improvement (see below) is recommended but not implemented in this pass.**

**History of this finding, corrected twice — read in order:**
1. First pass (closeout): 4 intermittent failures under default `workers: 2`. One isolation rerun made 3/4 pass → wrongly declared "confirmed CPU contention, harmless."
2. Second pass (after Product Office rejected that as insufficient rigor): repeated isolation reruns showed 2 of those tests failing even **completely alone** (`--workers=1`, single test) — ruling out "2-worker contention" as the mechanism, but root cause still undetermined.
3. **This pass — actual root cause found and directly demonstrated:**

**Method:** wrote a standalone Node+Playwright diagnostic script replicating `stress.spec.ts`'s "10 consecutive large target-size jobs" loop exactly (same fixture, same selectors, same waits), instrumented to log per-iteration wall-clock time, live Blob URL count (via the same tracker `installBlobUrlTracker` installs), `performance.memory.usedJSHeapSize`, and DOM node count.

- **Run 1 (no tracing, direct Playwright):** all 10 iterations completed in a rock-steady ~3.5s each (41s total). Live Blob URLs constant at 2. JS heap constant at 10MB. DOM nodes constant at 1039. **Zero drift, zero leak, zero slowdown.**
- **Run 2 (identical script, only difference: `context.tracing.start({screenshots:true, snapshots:true})` enabled** — i.e., exactly what `playwright.config.ts`'s `trace: 'retain-on-failure'` does during every test): the **exact same erratic multi-second-spike pattern** appeared (iterations 0–4: 5.8–7.9s; iteration 5: 29.7s; iteration 6: 26.2s; then back down to 5.7–8.1s) — while the application-level metrics (Blob URLs, JS heap, DOM nodes) remained **identically flat** to Run 1.
- Ran the equivalent diagnostic for the Transparent Logo Pack cycle too (untraced): all 5 cycles + Original-mode cycle + cancel/retry completed in ~31s total, flat resource usage, no leak.
- Independently confirmed via the real trace of an actual test failure: `image.worker-*.js` was fetched 8 times across 9 iterations — this is **correct, intended architecture** (`worker-client.ts` creates a new `Worker` per job and calls `.terminate()` in `finish()` for every job, matching ADR-009's "one worker per heavy job" design), not a leak.

**Conclusion:** the intermittent timeouts in `stress.spec.ts`'s heaviest tests (and, per the broader Chromium/Firefox/WebKit runs below, in `processing-transition.spec.ts` and `network-privacy.spec.ts` too) are caused by **Playwright's own tracing/screencast/DOM-snapshot recording overhead** occasionally spiking during sustained real WASM/canvas work, not by any product-side resource leak, worker-lifecycle defect, or state-transition bug. The application itself is measurably fast, clean, and resource-bounded. This is a genuine, demonstrated **test-infrastructure** root cause (tracing overhead colliding with fixed step timeouts on long, single-session, heavy-processing tests), most visible on Firefox (22/254 failures in a from-scratch full run — nearly all concentrated in `processing-transition.spec.ts`, `stress.spec.ts`, and `network-privacy.spec.ts`) and present, less severely, on Chromium and in the governed WebKit CI environment too (see item 11).

**Fix applied (2026-09-24, Product Office-authorized):** `tests/browser/specs/stress.spec.ts` now declares a file-scoped `test.use({ trace: 'off' })` at the top of the file (must be top-level, not inside `test.describe` — Playwright requires this since a per-file trace override forces a dedicated worker), with a comment documenting the full evidence trail above. **No timeout was widened, no retry added, no assertion weakened, and no test skipped.** Tracing remains fully active for every other spec file and the global config is untouched. Ordinary `screenshot: 'only-on-failure'` (project-wide) is unaffected — a real failure still produces a screenshot, just no trace.zip for this one file.

**Verification (repeated runs, `--repeat-each`, chromium, this machine):**
- Batch 1: `--repeat-each=3` (15 test runs) → 14 passed, 1 failed (Transparent Logo Pack cycle, once).
- Batch 2: `--repeat-each=5` (25 test runs) → 25 passed, 0 failed, in 5.9 minutes (versus ~15-20 minutes for equivalent traced runs).
- **Combined: 39/40 (97.5%) pass rate**, a dramatic improvement over the pre-fix baseline (which included failures even running one test completely alone). Not literally 100% — some residual, much lower-probability timing variance remains, consistent with these tests still doing substantial real, cumulative WASM/canvas work; this is expected and was not chased further given the tracing-overhead cause is now removed and the failure rate is an order of magnitude lower.
- Full governed Chromium suite re-run with the fix in place: see item 12b below for the consolidated result.

## 10. Dark-mode GO-checkmark test: ROOT CAUSE FOUND — CSS-transition sampling race in the test, product visual output confirmed correct

**Status: RESOLVED (root cause identified, product confirmed correct, no fix needed).** `processing-transition.spec.ts:680` ("Dark mode: the completed GO checkmark renders white on the accent-blue fill") failed once across ~11 observed executions this session (one capture: expected `rgb(255,255,255)`, received `rgb(234,236,240)`).

**Root cause, confirmed against source:** `.fsg-processing-rail__node` (`resources/css/app.css:1359`) declares `transition: border-color 220ms ease, background-color 220ms ease, color 220ms ease`. The GO node's `color: #ffffff` is set only by the `[data-phase='ready']` rule (`app.css:1456-1463`); before that, it has no explicit color (inherits a much lighter but non-white tone). The test samples `getComputedStyle(...).color` immediately after `#fsg-processing-overlay-title` shows "Your file is ready," without waiting for the 220ms `color` transition to finish. `rgb(234,236,240)` is a value partway through that 220ms animation — i.e., the test occasionally samples mid-transition. This is a **test synchronization defect**, not a product defect: no user ever perceives an intermediate color (220ms is imperceptible), and this was independently confirmed by directly measuring the *settled* color programmatically — `rgb(255,255,255)` in **both** light and dark mode — plus fresh screenshots of both themes showing the correct white-on-blue checkmark.

**Reproducibility:** failed once in ~11 total executions (isolated reruns: 3/3 passed after the one observed failure) — a rare, low-probability race, fully consistent with sampling occasionally landing inside a 220ms window.

**Fresh evidence captured:** light-mode and dark-mode screenshots of the settled `ready` state (FILE/SET/GO rail), both showing the correct high-contrast white checkmark on the accent-blue GO node, per FSG-007-FIT-003-R5.1 directive §6/§7's explicit design intent (documented in the same CSS block as "the one deliberate exception to reusing `--fsg-surface` here").

**Fix applied (2026-09-24, Product Office-authorized):** `processing-transition.spec.ts:680`'s one-shot `page.locator(...).evaluate((el) => getComputedStyle(el).color)` + plain `expect(color).toBe(...)` replaced with `await expect(locator).toHaveCSS('color', 'rgb(255, 255, 255)')` — Playwright's web-first assertion, which polls/retries against the live computed style until it matches or its own timeout elapses. This deterministically waits out the 220ms transition without an arbitrary sleep, without touching the real CSS transition itself, and without changing the expected final color. Verified: 8/8 passed on repeated runs (`--repeat-each=8`).

## 11. New finding: mobile hero "three deliberate lines" overflow — reproducible on Linux CI, never reproduced locally (macOS)

**Status: OPEN — genuine, unresolved, not caused by any change in this session.** Running the governed WebKit CI workflow (`fsg-006-browser-certification.yml`, triggered via `workflow_dispatch` against the already-pushed `fsg-007-front-facing-redesign` branch at `ee9207a` — no new commit or push was made to trigger this) surfaced a **new, 100%-reproducible-in-CI, cross-engine** failure not seen in any of this session's ~6 full local runs: `header-navigation.spec.ts:261` ("keeps the mobile hero to three deliberate lines at governed widths") failed identically in **Chromium, Firefox, and WebKit** on the Linux CI runner — `geometry.lineCount` correctly equals 3, but `geometry.overflowing` is `true` (a hero line's `scrollWidth > clientWidth`) at one of the tested widths (320/375/390/430).

**Investigated directly:** wrote a diagnostic reproducing the test's exact measurement locally (macOS, Chromium) at all four widths — `scrollWidth === clientWidth` exactly (zero overflow) at every width, every time. **This test has never once failed locally in this session**, across the original closeout run, the post-revert run, and this final run — only in the Linux CI environment, in all three engines simultaneously.

**Leading hypothesis, substantially narrowed (still not conclusively confirmed on Linux itself):**

1. Confirmed `Instrument Sans`'s generated `@font-face` rules (`public/build/assets/fonts-*.css`) all declare **`font-display: swap`** — the browser renders text with its fallback font stack (`ui-sans-serif, system-ui, sans-serif, ...`) immediately, then swaps to the real font once loaded. This is a genuine FOUT (flash-of-unstyled-text) window, not a hypothetical one.
2. Confirmed the production build's own console output warns: *"Optimized font fallbacks require the optional 'fontaine' package"* — `fontaine` (which generates a metrically-matched fallback font using `size-adjust`/`ascent-override` so the fallback and final font occupy near-identical width) is **not installed**. The fallback font's metrics are therefore completely unadjusted relative to Instrument Sans.
3. **Directly tested the hypothesis locally:** forced the fallback font (permanently blocking the webfont network requests via Playwright route interception) and re-measured hero-line geometry at all four governed widths, in both Chromium and Firefox. **Result: zero overflow, even with the fallback font forced**, on this macOS host. macOS's `ui-sans-serif`/`system-ui` fallback (San Francisco) happens to be metrically close enough to Instrument Sans Bold at these sizes that it doesn't overflow.
4. This **does not disprove the hypothesis for Linux** — it specifically shows the *mechanism* (unadjusted-fallback-font-during-swap) is real and architecturally present, but that macOS's particular fallback font doesn't trigger it, while Ubuntu's typical fallback stack (DejaVu Sans / Liberation Sans / Noto Sans, whichever the GitHub Actions runner image provides) may have different, wider metrics for this text at this weight — that part remains unconfirmed.

**Why this could not be taken further in this pass:** closing this definitively requires either (a) adding temporary diagnostic instrumentation to the test and running it on the actual Linux CI runner, which requires a commit/push this session is explicitly not authorized to make, or (b) a local Linux/Docker environment to reproduce directly — Docker is not installed on this host, and no Linux environment was otherwise available. The governed CI run's own artifact upload step (`actions/upload-artifact@v4`) also produced no retrievable artifact for this run (`gh run download` / `gh api .../artifacts` both returned empty — a separate, minor CI infrastructure gap worth fixing independently), so the failure's own screenshot/trace could not be pulled for further offline analysis either.

**Recommendation, not applied (per explicit instruction not to guess a typography fix without confirmed cause):** the lowest-risk next step is a one-line test correction — insert `await page.evaluate(() => document.fonts.ready)` before measuring geometry — which resolves cleanly either way: if CI goes green after that, this was a font-loading race (test correction only, matching the decision tree's first branch); if CI still fails after that, the fallback-metrics mechanism is confirmed as the cause even post-swap (which would be surprising, since `fonts.ready` should mean Instrument Sans is already active), pointing to a genuine, different Linux-rendering explanation requiring fresh investigation rather than the fallback-font theory. Recommend this one-line addition be tried by whoever has push access, watching the very next CI run's result on this specific test.

**Not a regression from this session's changes:** this is present in the pushed `ee9207a` commit exactly as-is; no CSS or hero markup was touched in this session (the earlier mobile-trust CSS attempt was fully reverted, see item 3c history).
